## 주요 프로젝트 경험

### 프로젝트 1. Dentbird Linker — 웹↔로컬 CAM 디바이스 브리지
`2024.07 ~ 2025.12 (이후 Solutions 통합, 2026.06까지 단독 운영)` · 아키텍처 설계·구현 주도 (초기 검증은 타인, 프로덕션화·재설계·장기 운영은 본인 단독)

Dentbird에서 생성한 보철 케이스를 외부 CAM 소프트웨어로 보내려면 다운로드·압축 해제·수동 투입을 거쳐야 했고, 자체 로컬 서버가 없는 CAM은 연동 자체가 불가능했습니다. 여기에 Chrome LNA(Local Network Access) 정책이 브라우저→로컬 통신을 막으면서 기존 로컬 서버 방식이 동작을 멈췄고, 이를 Custom Protocol 중간 레이어로 재설계했습니다.

▸ 기여
- 웹↔로컬 연동을 Custom Protocol 기반 중간 레이어로 재설계 *(기존 로컬 서버 방식 폐기 — 브라우저가 앱을 깨워 세션 위임 → 앱이 클라우드에서 파일 self-fetch → 변환 후 CAM 실행)*
- 이질적인 외부 CAM **12종**의 좌표계·파일 전달 방식 차이를 단일 변환·연동 인터페이스로 추상화
- 명확한 스펙이 없는 기존 연동을 특성화 테스트로 고정한 뒤 구현으로 통과시키는 방식 채택 *(버그 수정이 곧 살아있는 스펙)*
- Datadog 연동으로 데스크톱 앱 운영 관측성 확보 — 출시 이후 안정화·연동 확장을 2026년까지 단독 책임 *(딥링크·세션·CAM 연동 이슈를 지속 담당)*

▸ 판단·정책
- AI를 활용해 LNA 우회 20여 방안을 폭넓게 탐색한 뒤 장기 안정성 기준으로 Custom Protocol 채택 — WebSocket은 구현이 빠르나 '곧 LNA 적용 예정'이라 1~2년 후 재차단될 단기 해법으로 탈락, HTTPS 로컬 서버는 LNA가 네트워크 위치(public→private) 기반이라 무효
- 연동을 '데이터 채널(파일 전달)'과 '감지 채널(앱 설치·실행 여부 회신)'로 분리해 프레이밍 — 데이터 전달은 Custom Protocol로 해결했으나, 장기 안정성을 위해 양방향성을 포기한 트레이드오프가 감지 채널 부채로 귀결
- 지속성·한계: 현재 앱 실행 감지는 포커스 변화 휴리스틱에 의존해 오탐 여지가 있고, 백엔드 왕복 폴링안은 서버 의존 확장을 피하려 보류 — 감지를 핵심 경로에서 빼는 방향으로 개선 검토 중

`기술` Electron · Vite · React · TypeScript · Custom Protocol · 특성화 테스트 · Datadog

### 프로젝트 3. 3D 렌더 품질 자동화 — 색·조명 정공법 재설계 + 자작 visual regression
`2026.04 ~ 현재` · 3D 뷰어 렌더 정합 재설계 · visual regression CI 토대 · 렌더 진입점 단일화 단독 (사내 3D → Three.js 전환 골격은 팀, 본인은 그 위 품질 레이어)

사내 3D 라이브러리에서 Three.js로 옮긴 뷰어는 두 엔진의 파이프라인 차이 탓에 색·조명이 어긋났고, 초기엔 감마 보정값으로 차이를 덮은 상태였습니다. 감마 우회를 걷어내고 SRGB 정공법으로 다시 풀되, 일반 픽셀 비교 도구가 못 잡는 mesh 렌더 회귀를 직접 만든 픽셀 metric으로 가드하는 데 집중했습니다.

▸ 기여
- 색·조명 정합을 감마 우회에서 SRGB 정공법으로 재설계 — 직전에 차이를 덮던 감마 보정값을 폐기하고, 색 공간·조명 비율을 명시적으로 맞춤
- 텍스처 좌표를 표준 디코딩 경로로 정공법 처리 *(메인 스레드에서 돌던 WASM 디코더 폐기 등 ~1,420줄 제거)*
- mesh 렌더 회귀를 직접 만든 픽셀 metric으로 가드하는 visual regression CI 구축 — 채널별 평균 픽셀 차이를 metric으로 정의하고, 소프트웨어 렌더러로 CI(Linux)와 로컬(macOS)의 GPU 차이를 흡수해 결정적으로 측정
- 3개 앱 공유 baseline을 단일 metric 세트로 운영 *(4 케이스 × 3 쌍 = 12 metric)* — 정상은 평균 0.0, 조명·색 공간 회귀 시 임곗값(2.0)을 넘긴 2.2865로 RED 차단 *(픽셀 비율 10% 허용의 일반 비교로는 못 걸리던 회귀)*
- 뷰어 mesh 변환을 단일 진입점(SoT)으로 통합 — 사전 로딩·폴백·향후 추가 경로가 모두 한 함수를 통과하도록 재설계 *(156개 명세·1,129개 테스트로 가드)*

▸ 판단·정책
- VTK 썸네일 엔진을 Three.js로 통합하지 않기로 결정 — 통합 시 번들·성능 이득을 실측으로 검증했으나 *(VTK 306파일·iwtk 649파일이 타 앱 핵심 엔진으로 잔존 → 번들 감소 0)* 이득이 없어 "생성은 VTK / 사후 재캡처는 Three.js" 책임 경계 공존으로 결론 — **'안 하는 결정'을 데이터로 정당화**
- 색 버그가 4번에 걸쳐 매번 다른 근본 원인으로 재발한 가족사를 규명하며, 단발 수정 대신 회귀 가드를 재사용 자산으로 세움 — DOM으로 검증 불가한 3D 렌더는 캔버스 픽셀 가드로, 데이터 빌더 미러링이 아닌 사용자가 보는 결과(E2E) 기준으로 검증
- 지속성: 마이그레이션 자체보다 그동안 안 보이던 2~3년 묵은 잠복 결함이 표면화되는 게 본질 위험이라 보고, '불변식 선행 → 폴백 안전망 → 근본 원인 별도 수정' 순서를 패턴으로 정립

`기술` Three.js · draco3d · Playwright · pngjs · swiftshader · WebGL · SRGB ColorManagement · Vitest

### 프로젝트 4. 품질 자동화 토대 — 커밋 단위 격리 재현 · E2E 통합 · AI 변경 감지
`2025.11 ~ 현재` · 격리 daily 진단·근본 수정 / AI 변경 감지 구축 전담 (격리 환경 위키 문서화는 팀)

공유 dev·qa 환경에 의존하던 E2E는 다른 변경의 간섭으로 결과가 흔들렸고, 전체 스위트를 매번 돌리느라 무인 회귀 검증이 무거웠습니다. 그래서 특정 커밋 시점을 결정론적으로 재현하는 격리 환경을 토대로 깔고, 만성적으로 실패하던 E2E를 근본 수정한 뒤, 변경과 연관된 테스트만 선별해 도는 자동 검증을 얹었습니다.

▸ 기여
- 커밋 시점의 클라이언트·서버·DB를 컨테이너로 격리 재현 — 다른 변경의 간섭 없이 시점을 결정론적으로 재현해 공유 환경 의존을 제거 *(daily 진단·근본 수정 전담, 환경 설계 위키는 팀)*
- 만성적으로 실패하던 격리 daily를 네 개 독립 원인으로 분리 진단한 뒤 두 건을 근본 수정 — 동시 빌드 다운로드 경합을 캐시 1회 선점 후 재사용으로 해소, 결제 테스트의 실행 경로 불일치를 정합화 *(결제 테스트 누락 ~28건 → 0, 통과 5 → 14)*
- 흩어져 있던 E2E를 모노레포로 통합 — Page Object 패턴으로 화면 변경을 한 곳에 가두고, 세션을 자동 발급·재사용하도록 만들어 중복을 제거
- 실행 인프라를 K8s에서 EC2로 재전환 *(운영 비용 월 ~$150 → ~$30)* — 선택 재실행·디버그 모드·즉시 반영을 얻으면서 상시 클러스터 유지비를 덜어냄
- **AI 변경 감지 E2E** 구축: 커밋 diff에서 변경 파일을 분석해 QA팀이 관리하는 테스트 케이스 중 연관 케이스를 선별·실행하고, 결과를 Teams로 보고하며, 실패를 실제 회귀와 테스트 코드 문제로 1차 분류 *(EC2에서 10분 주기 무인 운영)*

▸ 판단·정책
- 격리 daily의 만성 실패를 단일 앱 단위로 재현해 동시성을 유일 변수로 좁힌 뒤 근본 수정 — 증상 회피가 아니라 원인을 분리해 푸는 방식을 택함

### 프로젝트 5. 관측성·ErrorBoundary 표준 정렬 — 5개 앱을 팀 Datadog 표준에 정렬

### 프로젝트 8. 공통 모듈 통합(MFE) + 기업 랜딩 풀스택
`MFE 2024.11 ~ 2025.04 집중 · 랜딩 2023.09 ~ 2025.10` · MFE 초기 iframe 런타임 통합 주도 / 랜딩 v3 단독 리뉴얼 + Backoffice·서버 API 풀스택

cloud·crown·modeler·milling이 도메인도 관리팀도 나뉜 상황에서 공통 기능 4종(설정·내보내기·탐색기·뷰어)은 공유됐고, 하나가 바뀔 때마다 각 서비스에 같은 수정을 반복하고 전부 배포해야 했습니다. 이 반복을 줄이는 통합 전략을 정답 기술이 아니라 그때의 조직·배포 제약에 맞춰 재선택해 왔습니다. 한편 입사 첫 업무로 기업 랜딩 v3를 단독 리뉴얼하며 다국어·관리자 도구까지 풀스택으로 다뤘습니다.

▸ 기여
- 공통 기능 변경을 각 서비스 반복 수정에서 모듈 한 곳 수정으로 좁힌 **iframe + postMessage 런타임 통합** 주도 — cross-origin 격리 헤더와 호스트 화이트리스트 검증으로 임베드 경계를 잠금
- 랜딩 v3를 **단독 리뉴얼** *(v3 윈도우 커밋 점유 약 90%, 2위의 약 16배 · 이후 v3.0.x 47개 태그로 2년+ 단일 라인 운영)*

- 조직 관리 백오피스의 **그룹·팀·멤버 3계층 CRUD를 FE부터 서버 API까지** 1주 만에 동시 풀스택으로 완성 *(입사 3개월차 · 태그 일괄 수정 라우트 + 벌크 업데이트)*

▸ 판단·정책
- **빌드타임 통합 → iframe 회귀**: 모노레포 통합 후 빌드에 넣기 쉬워 빌드타임 통합으로 옮겼으나, 통합 배포가 실제론 거의 안 됐고 사내 배포 프로세스가 짧은 주기 배포를 어렵게 바뀌어 배포 부담이 커짐 → 다시 iframe으로 회귀하되 같은 origin으로 서빙해 CORS·인증 공유·origin 검증을 단순화 — 정답 기술 없이 조직·배포 제약에 맞춰 재선택
- **Module Federation은 써보고 이 건엔 제외**: 다른 기능에 직접 도입해본 결과 초기 설정과 소비처 설정 부담이 커 공통 모듈 통합에선 빼고, 콘솔 등 별도 서비스에는 적용 — 몰라서가 아니라 트레이드오프로 가른 판단
- 한계: iframe은 로딩 지연·라이브러리 중복 로딩·메시지 전송 제약이라는 비용을 직접 확인했고, 같은 모듈을 여러 개 동시에 여는 경우의 가드는 후속 과제로 남음

`기술` NX · iframe + postMessage · Module Federation · 타입세이프 i18n · Next.js · Fastify · MongoDB
