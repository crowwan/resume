2023.09부터 AI 기반 치과 CAD/CAM SaaS(Dentbird)에서, 화면 구현을 넘어 제품이 돌아가는 구조와 품질을 끝까지 책임지는 프론트엔드 개발자로 일해왔습니다.

### 프로젝트 1. Dentbird Linker — 웹↔로컬 CAM 디바이스 브리지
`2024.07 ~ 2025.12 (이후 Solutions 통합, 2026.06까지 단독 운영)` · 아키텍처 설계·재설계·단독 운영 (초기 검증은 타인, 프로덕션화·재설계·장기 운영은 본인 단독)

웹에서 생성한 보철 케이스를 사용자의 로컬 CAM 소프트웨어로 전달하는 데스크톱 앱. 기존엔 다운로드·압축 해제·수동 투입을 거쳐야 했고, 자체 로컬 서버가 없는 CAM은 연동 자체가 불가능했습니다.

- 초기 로컬 서버 방식이 Chrome LNA 정책에 막혀, AI를 활용한 20여 방안 비교 끝에 Custom Protocol 중간 레이어로 재설계
- WebSocket은 구현이 빠르나 곧 같은 LNA 정책에 막힐 단기 해법이라 제외, HTTPS 로컬 서버도 네트워크 위치 기반 정책상 무효 — 장기 안정성을 채택 기준으로
- 초기 핵심이던 로컬 서버를 직접 폐기 — 스스로 도입한 토대도 수명이 다하면 직접 거두는 판단
- 외부 CAM 12종의 제각각인 좌표계·파일 전달 방식을 단일 변환·연동 인터페이스로 통합
- 명확한 스펙이 없던 기존 연동을 특성화 테스트로 고정한 뒤 구현으로 통과시키는 방식 채택 — 버그 수정이 곧 살아있는 스펙
- Datadog 연동으로 데스크톱 앱 운영 관측성 확보, 딥링크·세션·CAM 연동 이슈를 2026년까지 단독 책임
- 데이터 전달은 풀었으나 장기 안정성을 위해 양방향성을 포기한 트레이드오프가 감지 채널 부채로 귀결
- 앱 실행 감지는 포커스 변화 휴리스틱 의존이 오탐 한계로, 핵심 경로에서 분리하는 방향으로 개선 중

`기술` Electron · Vite · React · TypeScript · Custom Protocol · 특성화 테스트 · Datadog

### 프로젝트 3. 3D 렌더 품질 자동화 — 색·조명 정공법 재설계 + 자작 visual regression
`2026.04 ~ 현재` · 렌더 정합 재설계·visual regression CI 토대·진입점 단일화 단독 (사내 3D → Three.js 전환 골격은 팀, 본인은 그 위 품질 레이어)

사내 3D 라이브러리에서 Three.js로 옮긴 뷰어는 두 엔진의 파이프라인 차이로 색·조명이 어긋났고, 초기엔 감마 보정값으로 그 차이를 덮은 상태였습니다.

- 색·조명 정합을 감마 우회에서 SRGB 정공법으로 재설계 — 차이를 덮던 보정값을 폐기하고 색 공간·조명 비율을 명시적으로 정합
- 텍스처 좌표를 표준 디코딩 경로로 정공법 처리, 메인 스레드에서 돌던 디코더 등 약 1,420줄 제거
- 일반 픽셀 비교가 못 잡는 mesh 렌더 회귀를, 채널별 평균 픽셀 차이를 metric으로 정의한 자작 도구로 가드하는 visual regression CI 구축
- 소프트웨어 렌더러로 CI와 로컬의 GPU 차이를 흡수해 결정적으로 측정, 3개 앱 공유 baseline을 단일 metric 세트로 운영 (4 케이스 × 3 쌍 = 12 metric)
- 뷰어 mesh 변환을 단일 진입점으로 통합 — 사전 로딩·폴백·향후 추가 경로가 모두 한 경로를 통과하도록 재설계
- 썸네일 엔진의 Three.js 통합은 번들·성능 이득을 실측으로 검증한 결과 이득이 없어 보류 — '안 하는 결정'을 데이터로 정당화
- 같은 색 버그가 네 번에 걸쳐 매번 다른 근본 원인으로 재발한 내력을 규명하며, 단발 수정 대신 회귀 가드를 재사용 자산으로 정립

`기술` Three.js · draco3d · Playwright · pngjs · swiftshader · WebGL · SRGB ColorManagement · Vitest

- 커밋 시점의 클라이언트·서버·DB를 컨테이너로 묶어, 다른 변경의 간섭 없이 그 시점을 결정론적으로 재현 — 공유 환경 의존 제거

- 실행 인프라를 K8s에서 EC2로 재전환해 선택 재실행·디버그·즉시 반영을 얻고 상시 클러스터 유지비 제거 — 운영비 월 약 $150에서 $30
- AI 변경 감지: 커밋 diff에서 변경 파일을 분석해 QA팀 qase 테스트 케이스 중 연관 케이스를 자동 선별·실행, Teams로 보고하며 실패를 실제 회귀와 테스트 코드 문제로 1차 분류 (EC2 10분 주기 무인 운영)
- 증상 회피가 아니라 동시성을 유일 변수로 좁혀 원인을 분리해 푸는 방식 선택 — 격리 컨테이너가 무거워져 재현용·수정용 이미지 분리를 검토 중
- AI 변경 감지는 daily 실패 누적으로 무인 운영을 멈추고 로컬 주기 실행으로 재편 중 — 구축·운영·한계까지 직접 겪은 영역

### 프로젝트 5. Electron 빌드·배포·자동 업데이트 인프라 — 담당자 PC 의존을 단독 운영 파이프라인으로
`2024 초기 설계 → 2026 GitHub Actions 이관 → 진행 중` · Batch·Linker 공통 인프라 중 최다 기여·단독 운영

두 데스크톱 앱의 빌드가 담당자 로컬 PC에서 돌려 올리는 구조라, 그 PC가 멈추면 빌드가 멈추고 Windows 서명 USB는 인프라팀을 매번 거쳐야 했던 출시 파이프라인을 재설계했습니다.

- macOS 빌드 파이프라인 재설계로 전체 33~39분을 17~24분으로 56% 단축, artifact 757MB→334MB·업로드 114→47초 동반 축소(PR 실측)
- Windows 코드 서명을 물리 빌드머신의 전용 서명 에이전트로 직접 설치·풀 등록 — CI 설정을 넘어 빌드 인프라 자체를 단독 운영하며 서명 USB·인프라팀 의존 제거
- 서명을 빌드 뒤 따로 하면 바이너리가 바뀌어 자동 업데이트가 깨지는 문제를 직접 겪고, 코드 서명을 빌드 과정 안에 통합
- 빌드머신이 사내 NAS로 직접 업로드하게 해, QA가 자동 업데이트를 기다리지 않고 최신 빌드를 즉시 받는 설치 경로 구축
- macOS 아키텍처를 Universal→arm64→Intel로 11일 만에 3연속 번복 — 용량 2배 트레이드오프를 도입·운영·회수까지 직접 감당한 판단
- blue-green은 도입했으나 green 검증 자동화는 환경·빌드가 2배가 되는 운영 비용 대비 가치를 따져 의도적 보류

`기술` electron-builder · electron-updater · GitHub Actions(self-hosted) · Azure Pipelines · 코드 서명·공증(notarization) · S3 · NAS · blue-green

### 프로젝트 6. 관측성·ErrorBoundary 표준 정렬 — 5개 앱을 팀 Datadog 표준에 정렬
`2026.04 ~ 현재` · EB→Datadog 정렬 종합 계획 author·5앱 통합 단독 주도 (관측 어휘 정의는 팀, 본인은 EB를 그 어휘에 정렬)

에러는 잡히지만 어디서 왜 났는지 추적되지 않던 상태였습니다. 같은 안전망이 모든 실패를 한 메시지로 흡수했고, 앱마다 ErrorBoundary와 관측 부착 방식이 제각각이었습니다.

- 3-layer ErrorBoundary 아키텍처(Root→Section→Feature) 설계·확립, 5개 앱 통합 — cloud-desktop·cloud-mobile·account·batch-web 완전, crown 부분
- EB→Datadog 표준 정렬 종합 계획을 author로 주도 — 의사결정 7차 개정·5개 PR 분해·EB↔Datadog 책임 분리
- 모든 실패가 한 에러 메시지로 collapse되던 Export 실패 124건을, 커스텀 에러 클래스와 RUM 직렬화로 root cause까지 추적 가능하게 재구성
- 최상위 Fallback에 디자인시스템·Hook·다국어 의존을 두지 않는 zero-dependency 원칙 확립 — 안전망이 자기 의존성 때문에 죽지 않도록
- 안전망은 발생 위치만 자동 표기하고 도메인 분류는 호출자가 명시하도록 분리 — 안전망과 의미부여의 책임을 떼어냄
- 직접 추가했던 7분류 에러 체계가 특정 앱에 편향됐다고 보고, 팀 Datadog 가시성 표준에 수렴시키며 자기 분류를 스스로 폐기

`기술` React · TypeScript · ErrorBoundary · Datadog RUM · 모노레포(NX)

### 프로젝트 7. Dentbird Account — B2B SaaS 구독·결제 FE
`2023.09 ~ 2025.07` · 구독제 전환 FE 전담 설계·구현

일회성 크레딧 결제에서 반복 구독 매출로 비즈니스 모델을 전환하며, 글로벌 멀티테넌트 환경의 결제·권한 도메인 FE를 전담했습니다. 결제는 정확성이 곧 신뢰라, 기능 구현을 넘어 부분 실패에도 무너지지 않는 검증 구조까지 함께 설계했습니다.

- 플랜 업그레이드·시트 구매·구독 취소/재개·쿠폰·결제수단·결제 히스토리까지 구독 워크플로우 전체를 레거시 크레딧 결제와 공존시키며 전담 구현
- 기존 별도 결제 팝업 앱에 Stripe 결제 페이지를 추가, 부모↔팝업 origin 격리 구조 위에서 결제 컨텍스트만 안전하게 주고받도록 연동
- HTTP 200으로 내려오는 서버의 비즈니스 에러를 커스텀 에러로 받아 코드별 분기 — 결제 정보를 못 받아도 내역 조회·구독 취소·뒤로가기는 살아남도록 Fault Tolerance를 도메인 의존 관계 기준으로 설계
- 결제 상태 동기화의 무한 폴링을 폴링 안전장치로 교정 — 기본 3초 간격·최대 20회 후 종료·언마운트 시 정리
- 구독을 만든 사람이 운영자(Backoffice) 측 구독 회귀 가드까지 작성 — 구현부터 품질까지 한 사람이 지는 종단 책임
- FSD·컴포넌트 패턴을 처음 본격 도입하며 과적용을 경험하고, 폴더 합의 비용·팀원별 해석 분기를 겪은 끝에 "기술 도입은 일관성이 아니라 우선순위 높은 문제부터"라는 기준으로 수렴 — 이후 모노레포 이관 뒤에도 에러 처리·도메인 분리 골격은 그대로 정착

`기술` React · TypeScript · react-query · Stripe · FSD · ErrorBoundary · Playwright(E2E)

### 프로젝트 8. 공통 모듈 통합(MFE) + 기업 랜딩 풀스택
`MFE 2024.11 ~ 2025.04 집중 · 랜딩 2023.09 ~ 2025.10` · MFE 초기 iframe 런타임 통합 주도 / 랜딩 v3 단독 리뉴얼 + Backoffice·서버 API 풀스택

cloud·crown·modeler·milling이 도메인도 관리팀도 나뉜 상황에서 공통 기능 4종(설정·내보내기·탐색기·뷰어)은 공유돼, 하나가 바뀔 때마다 각 서비스에 같은 수정을 반복하고 전부 배포해야 했습니다.

- 공통 기능 변경을 각 서비스 반복 수정에서 모듈 한 곳 수정으로 좁힌 iframe + postMessage 런타임 통합 주도 — cross-origin 격리 헤더와 호스트 화이트리스트로 임베드 경계 잠금
- 입사 첫 업무로 기업 랜딩 v3 단독 리뉴얼, 윈도우 커밋 점유 약 90%로 2위의 약 16배 — 이후 단일 라인으로 2년+ 운영
- 번역 키 오타가 런타임에야 원본 키로 노출되던 문제를, 영어 단일 소스에서 타입을 자동 생성해 없는 키를 컴파일 타임에 차단하는 방식으로 전환
- 조직 관리 백오피스의 그룹·팀·멤버 3계층 CRUD를 FE부터 서버 API까지 입사 3개월차에 동시 풀스택으로 완성
- 모노레포 통합 후 빌드타임 통합으로 옮겼으나 통합 배포가 거의 일어나지 않고 사내 배포 주기가 길어져, 같은 origin으로 서빙하는 iframe으로 회귀 — 정답 기술이 아니라 조직·배포 제약에 맞춘 재선택
- Module Federation은 다른 기능에 직접 도입해본 뒤 초기·소비처 설정 부담을 확인하고 이 건엔 제외, 별도 콘솔 서비스에만 적용 — 몰라서가 아니라 트레이드오프로 가른 제외
- iframe의 로딩 지연·라이브러리 중복 로딩·메시지 전송 제약을 직접 확인, 같은 모듈을 여러 개 동시에 여는 경우의 가드는 후속 과제로 남김

`기술` NX · iframe + postMessage · Module Federation · 타입세이프 i18n · Next.js · Fastify · MongoDB
