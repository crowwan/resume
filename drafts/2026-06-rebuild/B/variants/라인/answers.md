## Q1. 자신을 자유롭게 소개해 주세요.

저는 결제처럼 틀리면 곧바로 돈이 되는 흐름을, 화면 구현에서 끝내지 않고 검증과 테스트라는 구조로 끝까지 지키는 프론트엔드 개발자입니다. 제 일의 중심은 "이 화면이 보이는가"가 아니라 "부분 실패가 나도 이 흐름이 잘못된 결과를 내지 않는가"에 있습니다.

2023년 9월부터 이마고웍스에서 AI 기반 치과 CAD/CAM SaaS(Dentbird)의 프론트엔드를 맡아왔습니다. 입사 후 회사가 일회성 크레딧 판매에서 반복 구독 매출로 비즈니스 모델을 전환할 때, 글로벌 멀티테넌트·다국어 환경의 결제·권한 도메인 프론트엔드를 전담했습니다. 플랜 업그레이드, 시트 구매, 구독 취소와 재개, 쿠폰, 결제수단, 결제 히스토리까지 구독 워크플로우 전체를 레거시 크레딧 결제와 공존시키며 구현하는 동안, 결제는 기능이 동작하는 것만으로는 부족하고 부분 실패에도 무너지지 않는 검증 구조가 함께 있어야 신뢰가 된다는 것을 체감했습니다.

여기서 멈추지 않고 범위를 넓혀, 흩어진 앱을 NX 모노레포로 이관하고 공통 기능을 Micro Frontend로 분리하는 플랫폼 결정, 변경마다 격리된 환경에서 회귀를 검증하는 품질 자동화, Electron 데스크톱의 빌드와 코드 서명·배포 인프라까지 직접 설계하고 운영해왔습니다. 연차는 2년 9개월이지만, 한 제품 안에서 결제·플랫폼·품질·인프라를 폭넓게 전담한 밀도로 그 폭을 채워왔다고 생각합니다.

LINE Pay는 일본·대만·태국을 잇는 글로벌 크로스보더 결제라는, 제가 다뤄온 결제 도메인을 훨씬 큰 스케일에서 마주하는 자리입니다. 국가와 통화가 늘수록 "금액이 어긋나면 곧 돈"인 흐름은 더 많아지고, 그것을 화면 너머의 구조로 지켜야 한다는 제 일하는 방식의 가치도 함께 커진다고 봅니다. B2B 구독 결제에서 쌓은 결제 정확성 감각과 글로벌 멀티테넌트·다국어 경험을, 더 큰 사용자와 더 복잡한 국가·통화 환경에서 확장하고 싶어 지원합니다.

## Q2. LINE에서 왜 자신을 채용해야 하는지, 자신의 경쟁력에 대해 구체적으로 적어 주세요.

세 가지 경쟁력이 LINE Pay의 요구와 엔지니어링 문화에 직접 맞닿는다고 생각합니다.

**첫째, 결제 정확성을 구조로 지키는 프론트엔드.** 결제는 버그가 곧 금전 사고인 영역이라, 저는 기능 구현을 넘어 부분 실패에도 무너지지 않는 검증 구조까지 함께 설계해왔습니다. 서버가 HTTP 200으로 내려주는 비즈니스 에러를 커스텀 에러로 받아 코드별로 분기하고, 결제 정보를 받지 못해도 결제 내역 조회·구독 취소·뒤로가기 같은 핵심 흐름은 살아남도록 Fault Tolerance를 도메인 의존 관계 기준으로 설계했습니다. 결제 상태 동기화의 무한 폴링은 기본 간격·최대 횟수·언마운트 정리라는 안전장치로 교정했습니다. 화려한 효과 지표를 만들어 내세우기보다, 틀리면 돌이키기 어려운 흐름을 구조로 막아두는 쪽에 집중해왔다는 점을 강점으로 말씀드립니다.

**둘째, 글로벌 멀티테넌트와 타입세이프 다국어.** 다국가·다언어 환경에서 제품을 운영했고, 번역 키 오타가 런타임에야 원본 키로 노출되던 문제를 영어 단일 소스에서 타입을 자동 생성해 없는 키를 컴파일 타임에 차단하는 방식으로 전환했습니다. 다국어가 곧 결제 신뢰와 직결되는 LINE Pay의 다국가 환경에서, 사람이 매번 점검하지 않아도 누락을 빌드 단계에서 막아두는 구조가 필요하다고 보고, 그런 안전장치를 직접 세워본 경험이 있습니다.

**셋째, 격리 E2E와 AI 변경 감지 — LY의 PR 단위 격리 E2E 문화와 같은 방향.** 저는 공유 dev·qa 환경의 간섭으로 결과가 흔들리던 E2E를, 커밋 시점의 클라이언트·서버·DB를 컨테이너로 묶어 다른 변경의 간섭 없이 결정론적으로 재현하는 격리 환경 위로 옮겼습니다. LY가 PR 단위 격리 E2E를 엔지니어링 문화로 밀고 있다고 알고 있는데, 저는 이미 같은 철학으로 일해왔습니다. 나아가 JD가 필수로 둔 AI 기반 개발 도구와 관련해, 커밋 diff를 분석해 QA팀의 테스트 케이스 중 변경과 연관된 케이스만 자동 선별·실행하고 결과를 보고하는 변경 감지 시스템을 직접 만들어 테스트 파이프라인에 결합했고, 그 운영 한계까지 겪어봤습니다.

연차가 3년에 약간 못 미치지만, 결제·플랫폼·품질·AI를 한 제품에서 전담한 밀도로 그 차이를 충분히 상쇄할 수 있다고 생각합니다. 대규모 트래픽 환경의 성능 운영은 제가 LINE에서 새로 배우고 싶은 영역입니다.

## Q3. 대표적인 프로젝트 세 가지를 적어 주시되, 각각의 프로젝트에서 어떤 기술을 활용하여 어떤 방식으로 개발했는지 구체적으로 설명해 주세요.

### 1. B2B SaaS 구독·결제 시스템 — Dentbird Account

회사가 크레딧 기반에서 구독제로 비즈니스 모델을 전환하는 결제·권한 도메인의 프론트엔드를, 글로벌 멀티테넌트·다국어 환경에서 전담했습니다.

React·TypeScript·TanStack Query를 기반으로 플랜 업그레이드·시트 구매·구독 취소와 재개·쿠폰·결제수단·결제 히스토리까지 구독 워크플로우 전체를 레거시 크레딧 결제와 공존시키며 구현했습니다. 결제 자체는 기존 별도 결제 팝업 앱에 Stripe 결제 페이지를 추가하는 형태로 연동했고, 이때 부모 창과 팝업의 origin을 격리한 구조 위에서 결제 컨텍스트만 안전하게 주고받도록 했습니다.

이 프로젝트에서 가장 신경 쓴 부분은 정확성의 검증 구조입니다. 서버가 HTTP 200으로 내려주는 비즈니스 에러를 커스텀 에러 클래스로 받아 코드별로 분기하고, 결제 정보를 받지 못하더라도 결제 내역 조회·구독 취소·뒤로가기 같은 핵심 흐름은 살아남도록 Fault Tolerance를 도메인 의존 관계 기준으로 설계했습니다. 결제 상태 동기화의 무한 폴링은 기본 간격·최대 횟수·언마운트 정리라는 안전장치로 교정했습니다. 또한 구독을 만든 사람으로서 운영자 측 구독 회귀 가드까지 직접 작성해, 구현부터 품질까지 한 사람이 지는 종단 책임을 가져갔습니다. FSD와 컴포넌트 패턴을 처음 본격 도입하며 과적용도 겪었고, 그 경험을 통해 기술 도입은 일관성이 아니라 우선순위 높은 문제부터라는 기준으로 정리했습니다.

### 2. 플랫폼 아키텍처 — NX 모노레포 이관과 Micro Frontend

여러 클라이언트 앱이 환경별 도메인·URL을 제각기 구성하던 구조를, 도메인 파생을 한 곳으로 모으는 통합 라이브러리부터 세워 그 위에 플랫폼 인프라가 쌓이도록 토대를 잡았습니다. 이 통합 라이브러리는 이후 팀의 런타임 환경 분리와 격리 재현 환경이 얹히는 시작점이 되었습니다.

별도 레포에 흩어져 있던 클라이언트 앱 2종과 공용 라이브러리 6종을 메인 NX 모노레포로 이관했는데, Git Subtree Split으로 커밋 이력을 보존하고 네임스페이스 충돌을 리네임한 뒤 정기 동기화를 운영했습니다. 모노레포 도구는 새로 고르지 않고 기존 NX를 유지했는데, 이는 전환 이득이 이관·재학습 비용을 넘지 못한다고 본 비용-편익 판단이었습니다. 백지에서 고른 선택이 아니라, 이미 깔린 토대를 두고 바꿀 가치가 있는지 따진 결정이었습니다.

공통 기능 모듈화에서는, 네 개 서비스가 공유하는 공통 기능(설정·내보내기·탐색기·뷰어)을 iframe과 postMessage 기반 런타임 통합으로 묶어, 한 곳을 고치면 각 서비스에 반영되도록 했고 cross-origin 격리 헤더와 호스트 화이트리스트로 임베드 경계를 잠갔습니다. 이 과정에서 빌드타임 통합으로 옮겼다가 통합 배포가 거의 일어나지 않는 조직·배포 제약 때문에 다시 iframe으로 회귀하는 재선택을 경험했습니다. Module Federation은 다른 기능에 직접 도입해 소비처 설정 부담을 확인한 뒤 이 건에선 제외하는 트레이드오프 판단을 내렸습니다. 통합 전략에 절대적 정답 기술은 없고 조직과 배포 제약에 맞춰 재선택할 뿐이라는 것을 체득한 프로젝트입니다.

### 3. 품질 자동화 — 커밋 단위 격리 재현과 E2E 통합

테스트가 거의 없던 제품에, 변경마다 결정론적으로 검증되는 자동화 안전망을 구축했습니다.

공유 dev·qa 환경에 의존하던 E2E는 다른 변경의 간섭으로 결과가 흔들렸기 때문에, 커밋 시점의 클라이언트·서버·DB를 Docker 컨테이너로 묶어 다른 변경의 간섭 없이 그 시점을 결정론적으로 재현하는 격리 환경 위로 옮겼습니다. 만성적으로 실패하던 격리 데일리 검증을 네 개의 독립된 원인으로 분리 진단한 뒤 두 건을 근본 수정했는데, 동시 빌드 다운로드 경합은 캐시를 한 번 선점·재사용하는 방식으로 해소했고 누락돼 있던 결제 테스트 약 28건을 정합화해 통과 케이스를 5개에서 14개로 회복시켰습니다. 흩어져 있던 E2E는 모노레포로 통합하면서 Page Object 패턴으로 화면 변경을 한 곳에 가두고, 세션을 자동 발급·재사용해 반복 로그인 셋업의 중복을 제거했습니다. 실행 인프라는 상시 클러스터 유지비가 들던 K8s에서 EC2로 재전환해, 선택 재실행·디버그·즉시 반영을 얻고 상시 유지비를 월 약 150달러에서 30달러 수준으로 낮췄습니다.

기술적으로는 Playwright·Docker·MongoDB·EC2·GitHub Actions(self-hosted)를 사용했고, 증상을 회피하는 대신 동시성을 유일한 변수로 좁혀 원인을 분리해 푸는 방식을 택했습니다. 다만 격리 컨테이너가 점점 무거워지는 한계가 있어, 재현용 이미지와 수정용 이미지를 분리하는 방향을 검토하고 있습니다.

> (보조 프로젝트로, 웹에서 만든 보철 케이스를 사용자의 로컬 CAM 소프트웨어로 전달하는 Electron 앱을 설계·재설계·단독 운영했습니다. 초기 로컬 서버 방식이 Chrome의 로컬 네트워크 접근 정책에 막혀, 20여 개 방안을 비교한 끝에 Custom Protocol 중간 레이어로 재설계한 사례를 첨부 포트폴리오에 케이스 스터디로 정리해두었습니다.)

## Q4. 프로젝트 진행 중 가장 기억에 남는 트러블 슈팅 경험을 작성해 주세요.

**자동 업데이트가 조용히 실패하던 문제 — 무결성 검증의 전제를 추적하다**

Electron 데스크톱 앱의 자동 업데이트 인프라를 운영하던 중, 새 버전을 배포해도 클라이언트가 업데이트를 받지 못하는 현상이 있었습니다. 명시적인 에러가 뜨지 않아 원인을 좁히기 어려운 종류의 실패였습니다.

추적해보니 원인은 무결성 검증의 전제에 있었습니다. 자동 업데이트는 배포 메타데이터에 기록된 바이너리의 해시와 실제로 내려받은 파일의 해시를 대조하는데, 코드 서명 없이 빌드한 아티팩트를 나중에 따로 서명하면 바이너리가 바뀌어 해시가 어긋나고, 그 결과 업데이트가 무효화되고 있었습니다. 서명이라는, 자동 업데이트와는 무관해 보이는 단계가 실제로는 무결성 검증의 전제를 깨뜨리고 있었던 것입니다.

해결은 임시로 해시를 다시 계산해 맞추는 것이 아니라, 코드 서명을 빌드 과정 안에 통합해 "서명된 바이너리"가 곧 "해시가 기록되는 바이너리"가 되도록 파이프라인 자체를 구조적으로 바꾸는 것이었습니다. 이 과정에서 자동 업데이트 라이브러리가 무결성을 어떻게 검증하는지 내부 동작을 직접 확인하고, 운영 환경에 맞지 않던 부분을 정리했습니다.

이 경험이 기억에 남는 이유는, 증상이 아니라 검증의 전제 자체를 고쳤기 때문입니다. 금액이든 바이너리 무결성이든, 틀리면 돌이키기 어려운 검증은 임시방편이 아니라 구조로 고쳐야 한다는 것이, 결제 도메인을 다뤄온 제가 일하는 방식입니다.

## Q5. AI를 활용하여 생산성을 향상시킨 경험에 대해서 작성해 주세요.

**커밋 변경을 분석해 "필요한 테스트만" 자동으로 골라 실행하기**

전체 E2E를 매 커밋마다 돌리면 무겁고, 안 돌리면 회귀를 놓칩니다. 그렇다고 "이번 변경에는 이 테스트만"을 사람이 매번 고르는 방식은 오래 지속되기 어려웠습니다.

그래서 AI를 코드 자동완성 같은 보조 도구가 아니라, 개발 파이프라인의 판단 단계에 결합하기로 했습니다. 커밋 diff에서 변경된 파일을 분석해, QA팀이 관리하는 테스트 케이스 중 변경과 연관된 케이스만 자동으로 선별·실행하고, 결과를 Teams로 보고하며 실패를 실제 회귀와 테스트 코드 자체의 문제로 1차 분류하는 시스템을 만들었습니다. EC2에서 10분 주기로 무인 실행되도록 했고, 실행 기반으로는 앞서 제가 구축한 Docker 격리 재현 환경을 그대로 활용했습니다.

다만 정직하게 말씀드리면, 이 방식에는 분명한 한계가 있었습니다. 무인 운영 중 데일리 검증 실패가 누적되면서 안정적으로 돌리기 어려워졌고, 현재는 무인 운영을 멈추고 로컬에서 주기적으로 실행하는 워크플로로 재편하는 중입니다. 또한 선별 정확도나 실행량 절감 같은 정량 효과는 아직 측정 근거를 확보하지 못해, 효과를 수치로 단정하지 않고 메커니즘 중심으로 말씀드립니다.

그럼에도 이 경험을 가장 먼저 꺼내는 이유는, AI를 제품 기능이 아니라 개발 생산성 인프라로 직접 붙여보고 그 한계까지 운영하며 겪어봤기 때문입니다. 어디까지 맡길 수 있고 어디서부터는 사람이 다시 잡아야 하는지를, 만들어보고 한계를 만나는 과정에서 구체적으로 배웠다고 생각합니다. 일상 개발에서도 AI 코딩 도구를 코드 리뷰 보조와 반복 작업 자동화에 활용하고 있습니다.
