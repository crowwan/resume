### 1. 품질 자동화 토대 — 커밋 단위 격리 재현 · E2E 통합 · AI 변경 감지
`2025.11 ~ 현재`

공유 dev·qa 환경에 의존하던 E2E는 다른 변경의 간섭으로 결과가 흔들렸고, 매번 전체 스위트를 도느라 무인 회귀 검증이 무거웠습니다. 테스트를 더 짜기 전에, 흔들리지 않는 재현 환경부터 세웠습니다.

- 커밋 시점의 클라이언트·서버·DB를 컨테이너로 묶어, 다른 변경의 간섭 없이 그 시점을 결정론적으로 재현 — 공유 환경 의존 제거
- 만성적으로 실패하던 격리 daily를 네 개 독립 원인으로 분리 진단 후 두 건 근본 수정 — 결제 테스트 누락 약 28건을 0으로 정합화(통과 5→14)
- 흩어진 E2E를 모노레포로 통합 — Page Object로 화면 변경을 한 곳에 가두고 세션을 자동 발급·재사용해 중복 제거
- 실행 인프라를 K8s에서 EC2로 재전환해 선택 재실행·디버그·즉시 반영을 얻고 상시 클러스터 유지비 제거 — 운영비 월 약 $150에서 $30
- AI 변경 감지: 커밋 diff에서 변경 파일을 분석해 QA팀 qase 테스트 케이스 중 연관 케이스만 자동 선별·실행 → Teams로 보고하며 실패를 실제 회귀와 테스트 코드 문제로 1차 분류
- 증상 회피가 아니라 동시성을 유일 변수로 좁혀 원인을 분리해 푸는 방식 선택 — AI 변경 감지는 daily 실패 누적으로 무인 운영을 멈추고 로컬 주기 실행으로 재편 중, 구축·운영·한계까지 직접 겪은 영역

`기술` Playwright · Docker · MongoDB · EC2 · GitHub Actions(self-hosted) · Claude Code CLI · Teams Webhook

### 2. 플랫폼 토대 — 도메인 통합 라이브러리 · 모노레포 이관
`2024.06 ~ 현재`

여러 클라이언트 앱이 환경별 URL·도메인을 제각기 구성하고 별도 레포로 흩어져 있던 구조라, 공통 토대부터 세운 뒤 그 위에 플랫폼 인프라가 쌓이도록 모듈 경계를 다시 그었습니다.

- 환경별로 흩어진 도메인·URL 구성을 단일 라이브러리로 일원화 — 팀의 런타임 환경 분리·격리 재현 환경이 이 위에 얹히는 시작점 (런타임 환경 분리 자체는 팀 공동)
- 별도 레포의 클라이언트 앱 2종·공용 라이브러리 6종을 메인 NX 모노레포로 이관 — Git Subtree Split으로 커밋 이력 보존·네임스페이스 충돌 리네임·이후 정기 동기화 운영
- 산재한 다국어 관리(중복 업로드·14개로 흩어진 스크립트·분산 빌드 타겟)를 단일 스크립트로 중앙화
- NX 자동 타겟 추론이 일으키던 빌드 오류를 진단, 불필요한 산출물 설정 제거로 빌드 태스크 11개→9개 축소·메모리 부족 해소
- 모노레포 도구를 새로 고르지 않고 기존 NX 유지 — 전환 이득이 이관·재학습 비용을 넘지 못한다고 본 비용-편익 판단

`기술` TypeScript · NX 모노레포 · Git Subtree · i18n

### 3. 공통 모듈 통합(MFE) + 기업 랜딩 풀스택
`MFE 2024.11 ~ 2025.04 · 랜딩 2023.09 ~ 2025.10`

cloud·crown·modeler·milling이 도메인도 관리팀도 나뉜 상황에서 공통 기능 4종(설정·내보내기·탐색기·뷰어)은 공유돼, 하나가 바뀔 때마다 각 서비스에 같은 수정을 반복하고 전부 배포해야 했습니다.

- 공통 기능 변경을 각 서비스 반복 수정에서 모듈 한 곳 수정으로 좁힌 iframe + postMessage 런타임 통합 주도 — cross-origin 격리 헤더와 호스트 화이트리스트로 임베드 경계 잠금
- 입사 첫 업무로 기업 랜딩 v3 단독 리뉴얼, 윈도우 커밋 점유 약 90%로 2위의 약 16배 — 이후 단일 라인으로 2년+ 운영
- 번역 키 오타가 런타임에야 원본 키로 노출되던 문제를, 영어 단일 소스에서 타입을 자동 생성해 없는 키를 컴파일 타임에 차단하는 방식으로 전환
- 조직 관리 백오피스의 그룹·팀·멤버 3계층 CRUD를 FE부터 서버 API까지 입사 3개월차에 동시 풀스택으로 완성
- 모노레포 통합 후 빌드타임 통합으로 옮겼으나 통합 배포가 거의 일어나지 않고 사내 배포 주기가 길어져, 같은 origin으로 서빙하는 iframe으로 회귀 — 정답 기술이 아니라 조직·배포 제약에 맞춘 재선택
- Module Federation은 다른 기능에 직접 도입해본 뒤 초기·소비처 설정 부담을 확인하고 이 건엔 제외 — 몰라서가 아니라 트레이드오프로 가른 제외

`기술` NX · iframe + postMessage · Module Federation · 타입세이프 i18n · Next.js · Fastify · MongoDB

### 4. Dentbird Linker — 웹↔로컬 CAM 디바이스 브리지
`2024.07 ~ 2025.12 (이후 Solutions 통합, 2026.06까지 단독 운영)`

웹에서 생성한 보철 케이스를 사용자의 로컬 CAM 소프트웨어로 전달하는 데스크톱 앱. 자체 로컬 서버가 없는 CAM까지 연동해야 하고 Chrome LNA 정책이 브라우저→로컬 통신을 막은 상황에서 연동을 재설계했습니다.

- 초기 로컬 서버 방식이 Chrome LNA 정책에 막혀, 20여 방안 비교 끝에 Custom Protocol 중간 레이어로 재설계
- WebSocket은 구현이 빠르나 곧 같은 정책에 막힐 단기 해법이라 제외하고 장기 안정성을 채택 기준으로
- 초기 핵심이던 로컬 서버를 직접 폐기 — 스스로 도입한 토대도 수명이 다하면 직접 거두는 판단
- 외부 CAM 12종의 제각각인 좌표계·전달 방식을 단일 변환·연동 인터페이스로 통합
- 앱 실행 감지는 포커스 변화 휴리스틱 의존이 한계로, 핵심 경로에서 분리하는 방향으로 개선 중

`기술` Electron · Vite · React · TypeScript · Custom Protocol · Datadog

### 5. 3D 렌더 품질 자동화 — 정공법 재설계 + 자작 visual regression
`2026.04 ~ 현재`

Three.js로 옮긴 뷰어는 두 엔진의 파이프라인 차이로 색·조명이 어긋났고, 초기엔 감마 보정값으로 그 차이를 덮은 상태였습니다.

- 색·조명 정합을 감마 우회에서 SRGB 정공법으로 재설계 — 차이를 덮던 보정값을 폐기하고 메인 스레드에서 돌던 디코더 등 약 1,420줄 제거
- 일반 픽셀 비교가 못 잡는 mesh 렌더 회귀를, 채널별 평균 픽셀 차이를 metric으로 정의한 자작 도구로 가드하는 visual regression CI 구축 — 소프트웨어 렌더러로 CI·로컬 GPU 차 흡수, 3개 앱 공유 baseline을 단일 metric 세트로 운영
- 썸네일 엔진의 Three.js 통합은 번들·성능 이득을 실측한 결과 이득이 없어 보류 — '안 하는 결정'을 데이터로 정당화

`기술` Three.js · draco3d · Playwright · pngjs · swiftshader · WebGL · SRGB ColorManagement

## 보완하고 싶은 영역 (정직하게)

대규모 웹 트래픽 환경의 **Core Web Vitals 최적화·SSR·BFF**는 아직 실무 경험이 깊지 않습니다. Next.js 기반 풀스택(기업 랜딩 + Fastify 서버 API)으로 서버사이드 JS 런타임을 직접 다뤄봤고, SaaS 제품에서 런타임 환경 분리·번들 구조·빌드 성능은 깊게 파왔지만, 제 성능 경험은 웹 런타임(CWV)보다 빌드·인프라 쪽에 치우쳐 있습니다. 사용자 규모가 큰 웹 런타임 성능과 SSR/BFF 경계 설계는 입사 후 가장 먼저 채우고 싶은 영역입니다 — 오늘의집의 MSA FE 분리 기록이 제가 모노레포·MFE에서 다뤄온 경계 설계 문제와 결이 같아, 빠르게 따라붙을 수 있는 토대는 있다고 생각합니다.

**LLM 기반 사용자 인터랙션** 설계는 아직 직접 해보지 못했습니다. 다만 AI를 개발 파이프라인의 판단 단계(커밋 diff 분석 → 연관 테스트 선별)에 결합해 무인 운영과 그 한계까지 직접 겪어봤고, 이 감각을 사용자 대면 인터랙션 쪽으로 확장하는 데 관심이 큽니다.
