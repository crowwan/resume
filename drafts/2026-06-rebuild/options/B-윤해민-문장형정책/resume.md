## 간단 소개

화면을 만드는 데서 멈추지 않고, 그 화면이 의존하는 구조와 품질까지 끝까지 책임지려 합니다. 웹과 로컬 디바이스의 경계, 모노레포 토대, 3D 렌더 품질, 관측 표준처럼 눈에 잘 안 보이는 곳을 직접 설계하고 운영해 왔습니다. 기술 선택은 정답을 외우기보다 그때의 조직·배포 제약에 맞춰 트레이드오프로 가르는 편이고, 제가 내린 결정이 남긴 부채나 한계도 끝까지 따라가며, 제가 만든 분류가 팀 표준과 어긋나면 스스로 폐기합니다.

## 경력 — 이마고웍스 / 프론트엔드 · Dentbird 1 Team (2023.09~현재)

AI 기반 치과 CAD/CAM SaaS인 Dentbird의 프론트엔드를 맡으며, 도메인 통합 라이브러리로 플랫폼 토대를 깔고 웹↔로컬 디바이스 연동, 3D 렌더 품질 자동화, 격리 재현 기반 품질 인프라, 관측 표준 정렬, Electron 빌드·배포 인프라까지 폭넓은 기술 결정을 담당했습니다.

### 웹↔로컬 CAM 디바이스 브리지 (Dentbird Linker)
Dentbird에서 생성한 보철 케이스를 외부 CAM 소프트웨어로 보내려면 다운로드·압축 해제·수동 투입을 거쳐야 했고, 자체 로컬 서버가 없는 CAM은 연동 자체가 불가능했습니다. 게다가 Chrome의 로컬 네트워크 접근(LNA) 정책이 브라우저에서 로컬로의 통신을 막으면서 기존 로컬 서버 방식이 멈췄습니다.
- **역할**: 초기 검증은 다른 사람이 맡았고, 프로덕션화·재설계·장기 운영을 단독으로 담당. 딥링크로 데스크톱 앱을 호출해 세션을 위임하고, 앱이 서버에서 직접 파일을 받아 변환한 뒤 CAM을 실행하는 중간 레이어로 웹↔로컬 연동을 재설계. 좌표계·전달 방식이 제각각인 외부 CAM 12종을 단일 변환·연동 인터페이스로 추상화. 출시 이후 안정화와 연동 확장을 2026년까지 단독 책임.
- **정책**: LNA 우회 방안을 폭넓게(20여 가지) 탐색한 뒤 장기 안정성을 기준으로 Custom Protocol을 채택. WebSocket은 구현이 빠르지만 'LNA 적용 예정' 대상이라 1~2년 뒤 재차단될 단기 해법으로 탈락시켰고, HTTPS 로컬 서버는 LNA가 네트워크 위치(public→private) 기반이라 무효로 판단해 제외. 명확한 스펙이 없던 기존 연동은 특성화 테스트로 동작을 먼저 고정한 뒤 구현으로 통과시켜, 버그 수정이 곧 살아있는 스펙이 되도록 운영.
- **한계·지속성**: 연동을 데이터 채널(파일 전달)과 감지 채널(앱 설치·실행 여부 회신)로 나눠 보면, 데이터 전달은 풀었으나 장기 안정성을 위해 양방향성을 포기한 트레이드오프가 감지 채널의 부채로 남았습니다. 현재 앱 실행 감지는 포커스 변화 휴리스틱에 의존해 오탐 여지가 있고, 백엔드 왕복 폴링안은 서버 의존 확장을 피하려 보류한 채, 감지를 핵심 경로에서 빼는 방향으로 개선을 검토 중입니다.

### 플랫폼 토대 — 도메인 통합 라이브러리 · 모노레포 이관 (DentBird Solutions)
여러 클라이언트 앱이 환경별로 URL과 도메인을 제각기 구성하던 구조였습니다.
- **역할**: 도메인 파생을 한 곳으로 모으는 통합 라이브러리를 직접 설계해, 이후 팀이 진행한 런타임 환경 분리와 격리 재현 환경이 그 위에 쌓이는 시작점을 만듦. 별도 레포에 흩어져 있던 클라이언트 앱 2종과 공용 라이브러리 6종을 메인 NX 모노레포로 이관(커밋 이력 보존을 위한 Git Subtree Split·네임스페이스 충돌 리네임·이후 정기 동기화). 산재한 다국어 관리 스크립트를 단일 스크립트 묶음으로 중앙화.
- **정책**: 모노레포 도구는 새로 고르지 않고 기존 NX를 유지. 백지에서 고르는 상황이 아니라 이미 NX로 구성된 모노레포였고, 다른 도구로 바꿔 얻는 이득이 이관·재학습 비용을 넘지 못한다고 본 비용-편익 판단. 다만 NX 자동 타겟 추론이 일으키던 빌드 오류는 그대로 두지 않고, 불필요한 빌드 산출물 설정을 제거해 빌드 태스크를 11개에서 9개로 줄이고 메모리 부족(OOM)을 해결.

### 3D 렌더 품질 자동화 — 색·조명 정공법 재설계 + 픽셀 회귀 검출
사내 3D 라이브러리에서 Three.js로 옮긴 뷰어는 두 엔진의 파이프라인 차이 탓에 색·조명이 어긋났고, 초기엔 감마 보정값으로 차이를 덮어둔 상태였습니다. (엔진 전환 골격 자체는 팀 작업이고, 저는 그 위의 품질 레이어를 맡았습니다.)
- **역할**: 차이를 덮던 감마 보정을 걷어내고 색 공간·조명 비율을 명시적으로 맞추는 SRGB 정공법으로 재설계(메인 스레드에서 돌던 WASM 디코더 폐기 등 약 1,420줄 제거). 화면 픽셀 비교로는 못 잡는 mesh 렌더 회귀를, 채널별 평균 픽셀 차이를 지표로 정의한 회귀 검출 도구로 가드하는 시각 회귀 CI를 구축. 뷰어 mesh 변환을 단일 진입점으로 통합해 사전 로딩·폴백·향후 경로가 모두 한 함수를 통과하도록 재설계.
- **지표**: 소프트웨어 렌더러로 CI와 로컬의 GPU 차이를 흡수해 결정적으로 측정하고, 3개 앱이 공유하는 기준선을 단일 지표 세트(4 케이스 × 3 쌍 = 12개)로 운영. 정상은 평균 0.0이지만 조명·색 공간 회귀가 들어오면 임곗값(2.0)을 넘긴 2.2865로 빌드를 막아, 픽셀 비율 10%를 허용하는 일반 비교로는 걸리지 않던 회귀를 차단.
- **정책**: 별도의 썸네일 생성 엔진(VTK)을 Three.js로 통합하지 않기로 결정. 통합 시의 번들·성능 이득을 실측으로 검증했으나 해당 엔진이 다른 앱의 핵심으로 그대로 남아 번들 감소가 0이라, "생성은 기존 엔진, 사후 재캡처는 Three.js"라는 책임 경계 공존으로 결론. 안 하는 결정을 데이터로 정당화한 사례입니다. 색 버그가 네 차례에 걸쳐 매번 다른 근본 원인으로 재발한 가족사를 규명하면서, 단발 수정 대신 회귀 가드를 재사용 자산으로 세웠습니다.

### 품질 자동화 토대 — 커밋 단위 격리 재현 · E2E 통합 · AI 변경 감지
공유 dev·qa 환경에 의존하던 E2E는 다른 변경의 간섭으로 결과가 흔들렸고, 매번 전체 스위트를 돌리느라 무인 회귀 검증이 무거웠습니다.
- **역할**: 특정 커밋 시점의 클라이언트·서버·DB를 컨테이너로 격리 재현해, 다른 변경의 간섭 없이 시점을 결정론적으로 만들고 공유 환경 의존을 제거(격리 환경 설계 위키는 팀, 만성 실패 진단·근본 수정은 본인 전담). 흩어진 E2E를 모노레포로 통합하고 Page Object 패턴으로 화면 변경을 한 곳에 가둠.
- **지표**: 만성적으로 실패하던 격리 daily를 네 개의 독립 원인으로 분리 진단한 뒤 두 건을 근본 수정 — 동시 빌드 다운로드 경합을 캐시 1회 선점 후 재사용으로 해소하고, 결제 테스트의 실행 경로 불일치를 정합화(결제 테스트 누락 약 28건 → 0, 통과 5 → 14). 실행 인프라를 K8s에서 EC2로 재전환해 운영 비용을 월 약 $150에서 약 $30으로 낮춤.
- **정책**: 만성 실패를 증상 회피로 넘기지 않고, 단일 앱 단위로 재현해 동시성을 유일 변수로 좁힌 뒤 원인을 분리해 풀었습니다. 변경과 무관한 전수 실행이 무겁다는 문제는 **AI 변경 감지 E2E**로 풀었는데, 커밋 diff에서 변경 파일을 분석해 QA팀이 관리하는 테스트 케이스 중 연관된 것만 골라 실행하고, 결과를 Teams로 보고하며 실패를 실제 회귀와 테스트 코드 문제로 1차 분류하게 만들었습니다.
- **한계·지속성**: 격리 컨테이너가 점점 무거워져 성능 개선과 재현용·수정용 이미지 분리를 검토 중이고, AI 변경 감지는 daily 실패 누적으로 무인 운영을 잠시 멈추고 로컬 주기 실행으로 재편하는 중 — 구축부터 운영, 한계까지 직접 겪은 영역입니다.

### Electron 빌드·배포·자동 업데이트 인프라
두 데스크톱 앱(Batch·Linker)의 빌드는 처음엔 담당자 로컬 PC에서 돌려 올리는 구조라, 그 PC가 멈추면 빌드가 멈췄고 방법을 아는 사람이 담당자뿐이라 요청이 몰렸으며, Windows는 코드 서명 USB를 인프라팀이 쥐고 있어 매번 거쳐야 했습니다. (공통 Electron 인프라는 팀 작업이며, 본인이 최다 기여·단독 운영.)
- **역할**: self-hosted 빌드머신 위에서 코드 서명·자동 업데이트·blue-green 배포까지 데스크톱 출시 파이프라인 전체를 재설계해 단독 운영. macOS 빌드 파이프라인을 재설계해 전체 빌드 시간을 33~39분에서 17~24분으로(약 56%↓), 산출물을 757MB에서 334MB로, 업로드를 114초에서 47초로 줄임(모두 PR 본문 실측). Windows 코드 서명은 물리 빌드머신에 전용 서명 에이전트를 직접 설치하고 에이전트 풀에 등록해 두 앱 파이프라인이 동시에 돌도록 구성 — CI 설정을 넘어 빌드 인프라 자체를 운영하며 코드 서명 USB·인프라팀 의존을 제거.
- **정책**: 코드 서명을 빌드 뒤 따로 하면 바이너리가 바뀌어 자동 업데이트가 깨진다는 걸 직접 부딪혀 학습한 결과, 서명을 빌드 과정 안에 포함. macOS 빌드 아키텍처는 Universal → arm64 → Intel로 11일 만에 3연속 번복 — 앱 용량이 약 2배로 불어나는 트레이드오프를 직접 체감하고 되돌린 판단. blue-green 배포는 도입했으나, green 검증 자동화는 데스크톱 앱 특성상 환경·빌드가 2배가 되는 운영 비용 대비 가치를 따져 의도적으로 보류(현재는 실행 시 수동 플래그 확인).

### 관측성·ErrorBoundary 표준 정렬
에러는 잡히지만 어디서 왜 났는지 추적이 안 되던 상태였습니다. 같은 안전망이 모든 실패를 한 메시지로 흡수해 원인 파악이 막혔고, 앱마다 ErrorBoundary와 관측 부착 방식이 제각각이었습니다.
- **역할**: 5개 앱의 ErrorBoundary를 팀의 Datadog 관측 표준에 정렬하는 종합 계획서를 직접 작성·주도(의사결정 7차 개정 + 5개 PR 분해). 3-layer ErrorBoundary 아키텍처(Root→Section→Feature)를 설계해 4개 앱에 완전, 1개 앱에 부분 통합. 최상위 Fallback에 디자인시스템·Hook·다국어 의존을 두지 않는 원칙을 세워, 안전망이 자기 의존성 때문에 죽지 않게 함.
- **정책**: 직접 추가했던 에러 분류 체계(7분류)가 특정 앱에 편향돼 있다고 판단하고, 팀 전체가 범용으로 쓸 규칙이 필요하다고 봐서, 팀 Datadog 가시성 문서의 표준에 맞춰 자기 분류를 스스로 폐기·정렬. 관측 어휘 표준 자체는 팀이 정의했고, 저는 ErrorBoundary 라이브러리를 그 어휘에 맞추는 구현체를 맡았습니다. ErrorBoundary가 비즈니스 도메인을 자동 부여하지 않도록 설계해, 자동 경로는 발생 위치만 표기하고 도메인 분류는 호출자가 명시하게 함 — 안전망과 의미 부여의 책임을 분리.

### B2B SaaS 구독·결제 FE (Dentbird Account)
일회성 크레딧 결제에서 반복 구독 매출로 비즈니스 모델을 전환하면서, 글로벌 멀티테넌트 환경의 결제·권한 도메인 FE를 전담했습니다. 결제는 정확성이 곧 신뢰라, 기능 구현만이 아니라 흐름이 부분 실패해도 무너지지 않게 하는 검증 구조를 함께 설계했습니다.
- **역할**: 구독 워크플로우 전체(플랜 업그레이드·시트 구매·구독 취소/재개·쿠폰·결제수단·결제 히스토리)를 레거시 크레딧 결제와 공존시키며 전담 구현. 기존 별도 결제 팝업 앱에 Stripe 결제 페이지를 추가하고, 부모↔팝업 origin 격리 구조를 활용해 결제 컨텍스트만 안전하게 주고받도록 연동. 구독 기능을 만든 사람으로서 운영자(Backoffice) 측 구독 회귀 가드까지 작성해 구현부터 품질까지 종단으로 책임.
- **정책**: 서버가 HTTP 200으로 내려보내는 비즈니스 에러를 커스텀 에러로 받아 에러 코드별로 분기하되, 결제 정보를 못 받아도 결제 내역·구독 취소·뒤로가기 같은 핵심 흐름은 살아남도록 도메인 의존 관계 기준으로 내고장성을 설계. 결제 상태 동기화의 무한 폴링 버그는 기본 간격·최대 횟수·언마운트 정리를 갖춘 안전장치로 교정. FSD와 컴포넌트 디자인 패턴을 처음 본격 도입하며 과적용도 경험했는데, "기술 도입은 일관성이 아니라 우선순위 높은 문제부터"라는 기준을 그때 세웠습니다.
