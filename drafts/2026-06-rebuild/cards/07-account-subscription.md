**Dentbird Account — B2B SaaS 구독·결제 FE**
`2023.09 ~ 2025.07` · 구독제 전환 FE 전담 설계·구현

일회성 크레딧 결제에서 반복 구독 매출로 비즈니스 모델을 전환하면서, 글로벌 멀티테넌트 환경의 결제·권한 도메인 FE를 전담했습니다. 결제는 정확성이 곧 신뢰이므로, 기능 구현만이 아니라 결제 흐름이 부분 실패해도 무너지지 않게 하는 검증 구조를 함께 설계했습니다.

▸ 기여
- 구독 워크플로우 전체를 전담 구현 — 플랜 업그레이드·시트 구매·구독 취소/재개·쿠폰·결제수단·결제 히스토리 *(레거시 크레딧 결제와 공존)*
- 기존 별도 결제 팝업 앱에 Stripe 결제 페이지를 추가 — 부모↔팝업 origin 격리 구조를 활용해 결제 컨텍스트만 안전하게 주고받도록 연동 *(SUB-331 시트 추가 · SUB-387 결제 에러 처리)*
- 서버가 HTTP 200으로 내려보내는 비즈니스 에러를 커스텀 에러로 받아 에러 코드별로 분기 — 결제 정보를 못 받아도 결제 내역·구독 취소·뒤로가기 같은 핵심 흐름은 살아남도록 Fault Tolerance를 도메인 의존 관계 기준으로 설계
- 결제 상태 동기화의 무한 폴링 버그를 폴링 안전장치로 교정 *(기본 3초 간격 · 최대 20회 후 종료 · 언마운트 시 정리)*
- 구독 기능을 만든 사람이 운영자(Backoffice) 측 구독 회귀 가드까지 작성 — 구현부터 품질까지 한 사람이 종단 책임 *(구독 히스토리·플랜 다운그레이드 등 E2E 스위트)*

▸ 판단·지속성
- FSD와 컴포넌트 디자인 패턴을 처음 본격 도입하며 과적용을 경험 — 폴더 위치 합의에 드는 비용, 같은 패턴을 팀원마다 다르게 이해하는 분기를 겪고 "기술 도입은 일관성이 아니라 우선순위 높은 문제부터"라는 기준을 세웠습니다.
- 지속성: 구조 자체는 유효했기에 이후 모노레포 이관 후에도 에러 처리·도메인 분리 골격이 그대로 정착했습니다 — 배운 것은 구조의 옳고 그름이 아니라 도입의 전제(문제 정의·팀 공통 이해).

`기술` React · TypeScript · react-query · Stripe · FSD · ErrorBoundary · Playwright(E2E)
