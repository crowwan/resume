**3D 렌더 품질 자동화** — 색·조명 정합을 정공법으로 재설계하고, 픽셀 검사가 못 잡는 mesh 렌더 회귀를 자작 metric으로 차단
`2026.04 ~ 현재` · 3D 뷰어 렌더 정합 재설계 · visual regression CI 토대 · 렌더 진입점 단일화 단독 *(사내 3D → Three.js 전환 골격은 팀, 본인은 그 위 품질 레이어)*

사내 3D 라이브러리에서 Three.js로 옮긴 뷰어는 두 엔진의 파이프라인 차이 탓에 색·조명이 어긋났고, 초기엔 감마 보정값으로 차이를 덮은 상태였습니다. 감마 우회를 걷어내고 SRGB 정공법으로 다시 풀되, 일반 픽셀 비교 도구가 못 잡는 mesh 렌더 회귀를 직접 만든 픽셀 metric으로 가드하는 데 집중했습니다.

▸ 기여
- 색·조명 정합을 감마 우회에서 SRGB 정공법으로 재설계 — 직전에 차이를 덮던 감마 보정값을 폐기하고, 색 공간·조명 비율을 명시적으로 맞춤
- 텍스처 좌표를 표준 디코딩 경로로 정공법 처리 *(메인 스레드에서 돌던 WASM 디코더 폐기 등 ~1,420줄 제거)*
- mesh 렌더 회귀를 직접 만든 픽셀 metric으로 가드하는 visual regression CI 구축 — 채널별 평균 픽셀 차이를 metric으로 정의하고, 소프트웨어 렌더러로 CI(Linux)와 로컬(macOS)의 GPU 차이를 흡수해 결정적으로 측정
- 3개 앱 공유 baseline을 단일 metric 세트로 운영 *(4 케이스 × 3 쌍 = 12 metric)* — 정상은 평균 0.0, 조명·색 공간 회귀 시 임곗값(2.0)을 넘긴 2.2865로 RED 차단 *(픽셀 비율 10% 허용의 일반 비교로는 못 걸리던 회귀)*
- 뷰어 mesh 변환을 단일 진입점(SoT)으로 통합 — 사전 로딩·폴백·향후 추가 경로가 모두 한 함수를 통과하도록 재설계 *(156개 명세·1,129개 테스트로 가드)*

▸ 판단·지속성
- VTK 썸네일 엔진을 Three.js로 통합하지 않기로 결정 — 통합 시 번들·성능 이득을 실측으로 검증했으나 *(VTK 306파일·iwtk 649파일이 타 앱 핵심 엔진으로 잔존 → 번들 감소 0)* 이득이 없어, "생성은 VTK / 사후 재캡처는 Three.js" 책임 경계 공존으로 결론. **'안 하는 결정'을 데이터로 정당화**한 사례입니다.
- 색 버그가 4번에 걸쳐 매번 다른 근본 원인으로 재발한 가족사를 규명하며, 단발 수정 대신 **회귀 가드를 재사용 자산으로** 세움 — DOM으로 검증 불가한 3D 렌더는 캔버스 픽셀 가드로, 데이터 빌더 미러링이 아닌 사용자가 보는 결과(E2E) 기준으로 검증.
- 마이그레이션 자체보다 그동안 안 보이던 2~3년 묵은 잠복 결함이 표면화되는 게 본질 위험이라 보고, '불변식 선행 → 폴백 안전망 → 근본 원인 별도 수정' 순서를 패턴으로 정립.
