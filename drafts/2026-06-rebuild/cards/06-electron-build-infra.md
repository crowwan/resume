## Electron 빌드·배포·자동 업데이트 인프라 — 담당자 PC 의존을 단독 운영 파이프라인으로

`2024 초기 설계 → 2026 GitHub Actions 이관 → 진행 중` · Batch·Linker 공통 Electron 인프라(팀 작업, 본인 최다 기여·단독 운영)

두 Electron 데스크톱 앱(Batch·Linker)의 빌드가 처음엔 **담당자 로컬 PC에서 돌려 올리는 구조**라, 그 PC가 멈추면 빌드가 멈추고 방법을 아는 사람이 담당자뿐이라 요청이 몰렸으며, Windows는 코드 서명 USB를 인프라팀이 쥐고 있어 매번 거쳐야 했습니다. 당시엔 풀지 못한 채 팀 개편을 거쳤고, 빌드 파이프라인을 다시 맡으며 self-hosted 빌드머신 위에서 코드 서명·자동 업데이트·blue-green 배포까지 데스크톱 출시 파이프라인 전체를 재설계해 단독 운영하게 됐습니다.

**▸ 기여**

- macOS 빌드 파이프라인 재설계 *(전체 33~39분 → 17~24분, 56%↓ · artifact 757MB → 334MB, 56%↓ · 업로드 114초 → 47초, 59%↓ · PR 본문 실측)*
- Windows 코드 서명을 **물리 빌드머신에 전용 서명 에이전트를 직접 설치·에이전트 풀에 등록**해 Batch·Linker 양 앱 파이프라인이 동시에 돌도록 구성 — CI 설정을 넘어 **빌드 인프라 자체를 단독 운영**(코드 서명 USB·인프라팀 의존 제거)
- 코드 서명을 빌드 과정 안에 포함 — 서명을 빌드 뒤 따로 하면 바이너리가 바뀌어 자동 업데이트가 깨진다는 걸 직접 부딪혀 학습한 결과
- QA 빠른 설치 경로 설계: 빌드머신이 **사내 NAS에 직접 업로드**해, QA가 자동 업데이트를 기다리지 않고 최신 버전을 즉시 받게 함
- Azure 클라우드 러너의 느린 빌드를 **self-hosted 러너로 이관**(영구 캐시로 빌드 서버 부하 회피, 단계적 진행)

**▸ 판단·지속성**

- 자동 업데이트는 electron-builder 채택 — 기본 배포 모듈이 사내 호스트·인증과 맞지 않아 **라이브러리 내부를 직접 분석해 패치**한 뒤, 유지보수 부담을 줄이려 설정 커스텀 수준으로 단순화
- macOS 빌드 아키텍처를 Universal → arm64 → Intel로 **3연속 번복**(앱 용량이 약 2배로 불어나는 트레이드오프를 11일 만에 되돌림) — 도입 → 운영 한계 체감 → 번복까지 직접 판단
- 지속성: blue-green 배포는 도입했으나, green 검증 자동화는 데스크톱 앱 특성상 환경·빌드가 2배가 되는 **운영 비용 대비 가치**를 따져 의도적 보류(현재는 실행 시 수동 플래그 확인)
