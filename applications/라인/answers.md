## Q1. 자신을 자유롭게 소개해 주세요.

2023년 9월부터 이마고웍스에서 AI 기반 치과 CAD/CAM SaaS인 Dentbird의 프론트엔드를 맡고 있습니다. 화면 구현뿐 아니라 결제·구독 도메인, 모노레포·환경 분리, 테스트·빌드·배포 자동화까지, 제품이 돌아가는 구조를 담당해 왔습니다.

특히 회사가 일회성 크레딧 판매에서 반복 구독 매출로 전환하는 시점에 결제·권한 도메인의 프론트엔드를 전담했습니다. 플랜 업그레이드, 시트 구매, 구독 취소·재개, 쿠폰, 결제수단, 결제 히스토리까지 구독 워크플로우 전체를 글로벌 멀티테넌트·다국어 환경에서 구현했습니다. 결제는 틀리면 곧바로 신뢰가 깨지는 영역이라, 기능을 만드는 데서 멈추지 않고 외부 연동(서버·Stripe)의 복원력과 부분 실패 설계까지 챙기는 데 강점이 있습니다.

여기에 더해 NX 모노레포 통합, Playwright E2E를 커밋 시점 컨테이너로 격리해 재현하는 환경, 에러 관측 표준화 같은 품질 자동화까지 범위를 넓혀 왔습니다.

연차는 3년이 채 되지 않지만, 한 제품 안에서 결제·플랫폼·품질·인프라를 폭넓게 전담한 밀도로 그 폭을 채워 왔다고 생각합니다. LINE Pay는 일본·대만·태국을 잇는 글로벌 크로스보더 결제라는, 제가 다뤄온 결제 도메인을 훨씬 큰 스케일에서 마주하는 자리라 지원합니다.

## Q2. LINE에서 왜 자신을 채용해야 하는지, 자신의 경쟁력에 대해 구체적으로 적어 주세요.

세 가지 경쟁력이 LINE Pay의 요구·문화와 직접 맞닿는다고 생각합니다.

**1. 결제 정확성을 구조로 지킨 경험.** 결제는 버그가 곧 금전 사고로 이어지는 영역입니다. 구독·결제 도메인을 프론트엔드에서 전담하며, 기능 구현과 함께 외부 연동의 복원력을 구조로 챙겼습니다. 서버가 HTTP 200으로 내려주는 비즈니스 에러를 커스텀 에러로 받아 코드별로 분기했고, 결제 상태는 서버·Stripe 동기화를 기준으로 폴링해 UI에 반영하되 무한 반복을 막는 안전장치(3초 간격·최대 20회·언마운트 정리)를 추가했습니다. 나아가 결제 정보를 받지 못해도 결제 내역 조회·구독 취소·뒤로가기는 살아남도록 의존 관계 기준 Fault Tolerance를 제안했습니다(착수 전).

**2. 글로벌 멀티테넌트·다국어를 다뤄온 폭.** 일본을 포함한 글로벌 멀티테넌트 환경에서 결제·권한 도메인을 운영했습니다. 번역 키 오타가 런타임에야 드러나던 문제를, 영어 단일 소스에서 타입을 자동 생성해 없는 키를 컴파일 타임에 차단하는 타입세이프 i18n으로 전환한 경험이 있습니다. LINE Pay처럼 다국가·다통화·다언어가 본질인 결제 환경에서 필요한 감각이라고 생각합니다.

**3. 격리 E2E와 AI를 테스트 파이프라인에 결합한 경험.** 테스트가 거의 없던 제품에, 커밋 시점의 클라이언트·서버·DB를 하나의 컨테이너로 통합해 다른 변경의 간섭 없이 그 시점을 재현하는 환경을 만들었습니다. LY가 PR 단위 격리 E2E를 엔지니어링 문화로 밀고 있다는 점을 알고 있는데, 변경마다 격리된 환경에서 회귀를 검증하는 같은 철학으로 일해 왔습니다. 그 위에 커밋 변경을 분석해 연관 테스트만 자동 선별·실행하는 AI 변경 감지를 얹었습니다. JD가 필수로 두는 AI 기반 개발 도구를 단순 코딩 보조를 넘어 테스트 파이프라인의 판단 단계에 결합한 경험입니다.

연차가 3년에 약간 못 미치지만, 결제·플랫폼·품질을 한 제품에서 전담한 밀도로 그 차이를 충분히 상쇄할 수 있다고 생각합니다. 대규모 트래픽 환경의 성능 운영은 LINE에서 배우고 싶은 영역입니다.

## Q3. 대표적인 프로젝트 세 가지를 적어 주시되, 각각의 프로젝트에서 어떤 기술을 활용하여 어떤 방식으로 개발했는지 구체적으로 설명해 주세요.

### ① B2B 구독·결제 시스템 프론트엔드 (Dentbird Account)

회사가 일회성 크레딧 결제에서 반복 구독 매출로 전환하는 시점에, 글로벌 멀티테넌트 환경의 결제·권한 도메인 프론트엔드를 전담했습니다.

- React·TypeScript·TanStack Query로 플랜 업그레이드·시트 구매·구독 취소·재개·쿠폰·결제수단·결제 히스토리까지 구독 워크플로우 전체를 구현했습니다.
- 기존에 운영하던 별도 결제 팝업 앱에 Stripe 결제 페이지를 추가하고, 부모·팝업 origin 격리 구조 위에서 결제 컨텍스트만 안전하게 주고받도록 연동했습니다.
- 서버가 HTTP 200으로 내려주는 비즈니스 에러를 커스텀 에러로 받아 코드별로 분기하고, 결제 상태는 서버·Stripe 동기화를 기준으로 폴링해 UI에 반영하되 무한 반복을 막는 안전장치(3초 간격·최대 20회·언마운트 정리)를 추가했습니다. 나아가 결제 정보를 못 받아도 내역 조회·구독 취소·뒤로가기는 살아남도록 의존 관계 기준 Fault Tolerance를 제안했습니다(착수 전).

### ② 모노레포 통합·환경 분리

여러 클라이언트 앱이 환경별 URL·도메인을 제각기 구성하던 구조에, 도메인 파생을 한 곳으로 모았습니다.

- 환경별로 흩어진 도메인·URL 구성을 단일 통합 라이브러리로 일원화했습니다. 팀의 런타임 환경 분리와 격리 재현 환경이 이 라이브러리를 기반으로 동작합니다.
- 별도 레포의 클라이언트 앱 2종·공용 라이브러리 6종을 메인 NX 모노레포로 Git Subtree 이관했습니다. 커밋 이력 보존, 네임스페이스 충돌 리네임, 이후 정기 동기화까지 운영했습니다.
- NX 자동 타겟 추론이 일으키던 빌드 오류를 진단해, 불필요한 산출물 설정을 제거하고 빌드 태스크를 11개에서 9개로 줄여 메모리 부족을 해소했습니다.
- 모노레포 도구는 새로 고르지 않고 기존 NX를 유지했습니다. 전환으로 얻는 이득이 이관·재학습 비용을 넘지 못한다고 판단했기 때문입니다.

### ③ 테스트·품질 자동화 인프라

테스트가 거의 없던 제품에, 다른 변경의 간섭 없이 재현 가능한 환경 위에서 회귀를 자동으로 잡는 체계를 만들었습니다.

- 커밋 시점의 클라이언트·서버·DB를 하나의 컨테이너로 통합해, 다른 변경의 간섭 없이 그 시점을 결정론적으로 재현하도록 구성했습니다.
- 흩어진 Playwright E2E를 모노레포로 통합하고, Page Object와 세션 재사용으로 중복을 제거했습니다.
- 커밋 변경을 분석해 연관 QA 테스트 케이스만 자동 선별·실행하고, 결과를 Teams로 보고하며 실패를 실제 회귀와 테스트 코드 문제로 1차 분류하는 AI 변경 감지를 구축했습니다.
- 실행 인프라는 K8s로 구성하려다 복잡도가 높고 빠른 적용이 어렵다고 판단해, 더 단순하고 즉시 효과를 볼 수 있는 EC2로 선택했습니다.

> 보조 프로젝트로, 웹에서 만든 보철 케이스를 사용자 PC의 외부 CAM 소프트웨어로 넘기는 Electron 연동 앱을 설계·단독 운영한 경험이 있습니다. Chrome LNA 정책에 막힌 로컬 서버 방식을 Custom Protocol 중간 레이어로 재설계하고, 좌표계와 파일 전달 방식이 제각각인 외부 CAM 12종을 단일 인터페이스로 통합한 사례를 첨부 포트폴리오에 정리했습니다.

## Q4. 프로젝트 진행 중 가장 기억에 남는 트러블 슈팅 경험을 작성해 주세요.

**자동 업데이트가 조용히 실패하던 문제 — 무결성 검증의 전제 추적**

Electron 데스크톱 앱의 자동 업데이트를 구축하던 중, 새 버전을 배포해도 클라이언트가 업데이트를 받지 못하는 현상이 있었습니다. 에러가 명시적으로 뜨지 않아 원인을 좁히기 어려웠습니다.

추적해 보니, 자동 업데이트는 배포 메타데이터에 기록된 바이너리의 해시와 실제 내려받은 파일의 해시를 대조하는 구조였습니다. 코드 서명 없이 빌드한 아티팩트를 나중에 따로 서명하면 바이너리가 바뀌어 해시가 어긋났고, 업데이트가 무효화되고 있었습니다. 서명이라는, 업데이트와 무관해 보이는 단계가 무결성 검증을 깨뜨린 것이었습니다.

해결은 임시로 해시를 재계산해 맞추는 방식이 아니라, 코드 서명을 빌드 과정 안에 포함시켜 "서명된 바이너리"가 곧 "해시가 기록되는 바이너리"가 되도록 파이프라인을 구조적으로 바꾸는 것이었습니다. 이 과정에서 자동 업데이트 라이브러리 내부를 직접 분석해 무결성을 어떻게 검증하는지 확인하고, 운영 환경에 맞지 않던 부분은 패치했습니다.

증상이 아니라 무결성 검증의 전제 자체를 고친 경험으로 기억에 남습니다. 금액이든 무결성이든, 틀리면 돌이키기 어려운 검증은 임시방편이 아니라 구조로 고쳐야 한다는 것이 제가 일하는 방식입니다.

## Q5. AI를 활용하여 생산성을 향상시킨 경험에 대해서 작성해 주세요.

**커밋 변경에 필요한 테스트만 AI가 선별·실행하는 변경 감지**

전체 E2E를 매 커밋마다 돌리면 느리고, 안 돌리면 회귀를 놓칩니다. 그렇다고 이번 변경에는 어떤 테스트가 필요한지 사람이 매번 고르는 일은 지속되기 어려웠습니다.

그래서 커밋 범위의 변경 파일을 분석하고, QA팀이 관리하는 qase 테스트 케이스 중 연관된 것을 Claude가 선별해 해당 테스트만 실행하는 변경 감지를 구성했습니다. 실행 결과는 Teams로 보고하되, 실패를 실제 회귀와 테스트 코드 문제로 1차 분류하도록 했습니다. 예를 들어 단순히 셀렉터를 찾지 못해 실패한 케이스와 실제 API 회귀를 1차로 갈라, 사람이 확인할 것만 추려 보고하도록 했습니다. 이 시스템은 앞서 구축한 컨테이너 격리 재현 환경을 실행 기반으로 활용합니다.

핵심은 AI를 코드 자동완성 같은 보조 도구가 아니라, 어떤 테스트가 이 변경에 필요한가라는 판단 단계에 결합했다는 점입니다. 다만 한계도 분명합니다. AI의 연관 테스트 선별과 실패 분류는 1차 판단이라 사람의 확인이 필요하고, 실행 인프라의 보안 정책·스케줄 안정성에서도 운영 부담을 겪어 워크플로를 조정해 왔습니다. 선별 정확도나 실행량 절감 같은 정량 효과는 아직 측정 근거를 확보하지 못해, 메커니즘과 한계를 정직하게 두고 있습니다. 일상 개발에서도 AI 코딩 도구를 코드 리뷰 보조와 반복 작업 자동화에 활용하고 있습니다.
