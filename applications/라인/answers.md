## Q1. 자신을 자유롭게 소개해 주세요.

저는 **제품의 구조와 품질을 끝까지 책임지는 프론트엔드 개발자**입니다. 특히 결제처럼 틀리면 곧바로 돈이 되는 흐름을, 화면 구현에서 끝내지 않고 검증과 테스트로 지키는 일에 강점이 있습니다.

2023년 9월부터 이마고웍스에서 AI 기반 치과 CAD/CAM SaaS(Dentbird)의 프론트엔드를 맡아, 회사가 일회성 크레딧 판매에서 **반복 구독 매출로 전환하는 결제·구독 도메인의 프론트엔드를 전담**했습니다. 플랜 업그레이드, 시트 구매, 구독 취소/재개, 쿠폰, 결제수단, 결제 히스토리까지 결제 워크플로우 전체를 글로벌 멀티테넌트·다국어 환경에서 구현하면서, 금액이 어긋나기 쉬운 흐름의 정확성을 클라이언트 검증과 단위 테스트로 지키는 감각을 길렀습니다.

여기서 멈추지 않고 **플랫폼 아키텍처(NX 모노레포 통합·Micro Frontend·런타임 환경 분리)와 품질 자동화(Playwright E2E·Docker 격리 재현·AI 변경 감지 테스트)**, Electron 데스크톱과 빌드·배포 인프라까지 범위를 넓혀왔습니다. 연차는 2년 9개월이지만, 한 제품 안에서 결제·플랫폼·품질·인프라를 폭넓게 전담한 밀도로 그 폭을 채워왔다고 생각합니다.

LINE Pay는 일본·대만·태국을 잇는 글로벌 크로스보더 결제라는, 제가 다뤄온 결제 도메인을 훨씬 큰 스케일에서 마주하는 자리입니다. B2B 구독 결제에서 쌓은 결제 정확성 감각과 글로벌 멀티테넌트·다국어 경험을, 더 큰 사용자와 더 복잡한 통화·국가 환경에서 확장하고 싶어 지원합니다.

## Q2. LINE에서 왜 자신을 채용해야 하는지, 자신의 경쟁력에 대해 구체적으로 적어 주세요.

세 가지 경쟁력이 LINE Pay의 요구·문화와 직접 맞닿는다고 생각합니다.

**1. 결제 FE를 테스트로 지키는 사람.** 결제는 버그가 곧 금전 사고인 영역입니다. 저는 구독·결제 도메인을 FE에서 전담하며 구독 변경 같은 금액 정확성 흐름을 클라이언트 검증과 단위 테스트로 막아왔고, 동시에 Playwright E2E와 **커밋 시점의 클라이언트+서버를 Docker로 격리 재현하는 환경**을 직접 구축했습니다. LY가 PR 단위 격리 E2E를 엔지니어링 문화로 밀고 있다는 점을 알고 있는데, 저는 이미 같은 철학으로 일해왔습니다 — 변경마다 격리된 환경에서 회귀를 검증하는 방식입니다.

**2. AI를 개발 파이프라인에 결합해본 경험.** JD가 AI 기반 개발 도구 실무를 필수로 두고 있습니다. 저는 단순히 코딩 도구를 쓰는 수준을 넘어, **EC2에 Claude를 띄워 커밋 변경을 분석하고 관련 E2E만 자동 선별·실행하는 변경 감지 시스템**을 직접 만들어 테스트 파이프라인에 결합했습니다. 다만 EC2 보안 정책·스케줄 안정성의 운영 한계까지 겪고 현재는 로컬 데일리 워크플로로 재편 중인데, AI를 제품이 아니라 개발 생산성 인프라로 붙여보고 그 한계까지 운영해본 경험 자체가 강점이라고 생각합니다.

**3. 글로벌·플랫폼을 다뤄온 폭.** 글로벌 멀티테넌트·다국어 환경에서 제품을 운영했고, **번역 리소스의 타입을 자동 생성해 누락된 다국어 키를 컴파일 타임에 차단**하는 구조를 직접 도입했습니다. 분산된 앱을 NX 모노레포로 통합하고 공통 모듈을 Micro Frontend로 분리하는 플랫폼 결정을 주도했으며, Next.js·Node(Fastify) 기반 풀스택도 직접 개발했습니다. LINE Pay처럼 여러 서비스와 국가가 얽힌 대규모 조직에서 필요한 아키텍처 판단력입니다. (대규모 트래픽 환경의 성능 운영은 LINE에서 배우고 싶은 영역입니다.)

연차가 3년에 약간 못 미치지만(2년 9개월), 결제·플랫폼·품질·AI를 한 제품에서 전담한 밀도로 그 차이를 충분히 상쇄할 수 있다고 자신합니다.

## Q3. 대표적인 프로젝트 세 가지를 적어 주시되, 각각의 프로젝트에서 어떤 기술을 활용하여 어떤 방식으로 개발했는지 구체적으로 설명해 주세요.

### ① B2B SaaS 구독/결제 시스템 — Dentbird Account

회사가 크레딧 기반에서 구독제로 비즈니스 모델을 전환하는 결제·권한 도메인의 프론트엔드를, 글로벌 멀티테넌트·다국어 환경에서 전담했습니다.

- **기술/방식**: React·TypeScript·TanStack Query로 플랜 업그레이드·시트 구매·구독 취소/재개·쿠폰·결제수단·결제 히스토리까지 결제 워크플로우 전체를 구현했습니다. 구독 변경처럼 **금액이 어긋나기 쉬운 흐름**의 정확성을 클라이언트 검증과 단위 테스트로 확보했고, 한 기능의 오류가 전체 페이지를 멈추던 구조를 **ErrorBoundary 기반 선언적 에러 처리**로 기능 단위로 격리했습니다. 결제 정보를 받지 못해도 결제 내역·구독 취소·뒤로가기 같은 핵심 흐름은 살아남도록 Fault Tolerance를 설계했습니다.
- 서버가 HTTP 200으로 내려주는 비즈니스 에러를 커스텀 에러 클래스로 변환해 에러 코드별로 분기했고, FSD로 도메인을 분리하며 이 프로젝트에서 처음으로 테스트 코드를 도입했습니다.

### ② 플랫폼 아키텍처 — NX 모노레포 통합 & Micro Frontend

분산된 여러 프론트엔드 앱을 NX 모노레포로 통합하고, 4개 서비스가 공유하는 공통 기능(설정·내보내기·탐색기·뷰어)을 모듈화했습니다.

- **기술/방식**: 공통 기능을 라이브러리로 배포했다가 버전 업·재배포 반복 문제로 **iframe + postMessage 런타임 통합**으로 전환했습니다. Module Federation은 다른 서비스에 직접 도입해본 뒤 소비처 설정 부담을 확인하고 이 건에선 제외하는 트레이드오프 판단을 내렸습니다. 모노레포 통합 후 빌드타임 통합으로 옮겼다가 배포 부담으로 다시 iframe으로 회귀하며, "통합 전략에 정답 기술은 없고 조직·배포 제약에 맞춰 재선택할 뿐"임을 체득했습니다.
- 현재는 viewer의 렌더링 라이브러리를 Three.js로 전환하는 **팀 주도 작업에서 Viewer 렌더링 정합·회귀 수정을 담당**하고 있습니다.

### ③ 품질 자동화 — 격리 재현 & E2E

테스트가 거의 없던 제품에 자동화된 안전망을 구축했습니다.

- **기술/방식**: 환경변수를 빌드 시점 주입에서 **런타임 주입으로 전환**해 같은 번들 하나를 전 환경 공용으로 만든 뒤, 그 위에서 특정 커밋 시점의 클라이언트+서버를 **Docker로 격리 재현**하는 환경을 주도 구축했습니다. 잡마다 stateful 서비스를 새로 부팅하던 셋업 병목을 상태 보존 서비스 1세트 공유 모델로 바꿔, E2E 셋업을 **약 32분에서 3~5분으로 단축**했습니다. 흩어져 있던 E2E를 모노레포로 통합하고 Page Object 패턴으로 공통 플로우를 단일화했으며, 세션 자동 관리로 반복 로그인 셋업을 제거했습니다. 이 인프라 위에 EC2 Claude 기반 AI 변경 감지 자동화를 얹었습니다.

> (보조 프로젝트: 웹↔로컬 CAM 연동 Electron 앱 설계·구축, Chrome LNA 대응 Custom Protocol 채택, 빌드 파이프라인 20분대 → 6분 내외 — 첨부 포트폴리오에 케이스 스터디로 정리했습니다.)

## Q4. 프로젝트 진행 중 가장 기억에 남는 트러블 슈팅 경험을 작성해 주세요.

**자동 업데이트가 조용히 실패하던 문제 — 무결성 검증의 전제 추적**

Electron 데스크톱 앱의 자동 업데이트를 구축하던 중, 새 버전을 배포해도 클라이언트가 업데이트를 받지 못하는 현상이 있었습니다. 에러가 명시적으로 뜨지 않아 원인을 좁히기 어려웠습니다.

추적해보니, 자동 업데이트는 배포 메타데이터에 기록된 바이너리의 해시와 실제 내려받은 파일의 해시를 대조하는데, **코드 서명 없이 빌드한 아티팩트를 나중에 따로 서명하면 바이너리가 바뀌어 해시가 어긋나** 업데이트가 무효화되고 있었습니다. 서명이라는, 업데이트와 무관해 보이는 단계가 무결성 검증을 깨뜨린 것이었습니다.

해결은 임시로 해시를 재계산해 맞추는 게 아니라, **코드 서명을 빌드 과정 안에 포함**시켜 "서명된 바이너리"가 곧 "해시가 기록되는 바이너리"가 되도록 파이프라인을 구조적으로 바꾸는 것이었습니다. 이 과정에서 자동 업데이트 라이브러리 내부를 직접 분석하며 라이브러리가 무결성을 어떻게 검증하는지 확인하고, 운영 환경에 안 맞던 부분은 패치했습니다.

증상이 아니라 무결성 검증의 전제 자체를 고친 경험으로 기억에 남습니다. 금액이든 무결성이든 **"틀리면 돌이키기 어려운" 검증은 임시방편이 아니라 구조로 고쳐야 한다**는 것이, 결제 도메인을 다뤄온 제가 일하는 방식입니다.

> ⚠️ 제출 전 검토: 결제 도메인에서 직접 겪은 더 강한 트러블슈팅(예: 구독 변경 금액 불일치 재현·해결)이 있다면 그쪽이 LINE Pay에 더 적합할 수 있습니다. 실제 기억나는 사례로 교체 가능합니다.

## Q5. AI를 활용하여 생산성을 향상시킨 경험에 대해서 작성해 주세요.

**EC2 위의 Claude로 "바뀐 코드에 필요한 테스트만" 자동 실행하기**

전체 E2E를 매 커밋마다 돌리면 느리고, 안 돌리면 회귀를 놓칩니다. 그렇다고 "이번 변경엔 이 테스트만" 사람이 매번 고르는 것은 지속되기 어려웠습니다.

그래서 **EC2에 Claude를 상주시켜, 커밋의 변경 내용을 분석하고 변경과 관련된 E2E만 선별해 실행한 뒤 결과를 Teams로 보고하는 파이프라인**을 만들었습니다. 검증을 10분 주기로 자동화하고, 동시 실행과 중복 분석을 막는 장치를 두어 안정적으로 돌도록 했습니다. 이 시스템은 제가 앞서 구축한 Docker 격리 재현 환경을 실행 기반으로 활용합니다.

핵심은 AI를 코드 자동완성 같은 보조 도구가 아니라 **개발 파이프라인의 판단 단계(어떤 테스트가 이 변경에 필요한가)에 결합**했다는 점입니다. 다만 운영하면서 EC2 보안 정책과 스케줄 안정성의 한계를 겪어, 현재는 로컬 데일리 E2E 워크플로로 재편하고 있습니다. AI를 개발 생산성 인프라로 붙여보고 그 한계까지 직접 운영해본 경험이라고 생각합니다. 일상 개발에서도 AI 코딩 도구를 코드 리뷰 보조와 반복 작업 자동화에 활용하고 있습니다.

> ⚠️ 정량 효과(선별 정확도·실행량 절감 %)는 아직 측정 근거를 확보하지 못해 메커니즘 중심으로 기술했습니다. 면접에서 수치를 물으면 "측정 전이라 체감 기준"으로 정직하게 답하는 것을 권장합니다.
