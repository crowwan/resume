## 계정·구독 클라이언트 아키텍처 — FSD·컴포넌트 패턴과 도입 기준

`2023.09 ~ 2025.07` · `React · TypeScript · FSD`

> **성과** — 3개 앱에 중복되던 CaseInfo 다이얼로그를 Compound Component로 단일화해 약 66%(984→330줄) 감소, FSD·디자인 패턴의 도입 기준을 팀에 정립

![CaseInfo 다이얼로그 코드 — 3개 앱에 중복되던 984줄을 공통 컴포넌트 330줄로, 약 66% 감소](../../images/portfolio/diagrams/caseinfo-metrics.svg){.diagram}

### 문제

계정·구독 클라이언트를 입사 초기부터 오래 맡았는데, 코드 컨벤션이 구체적으로 정해져 있지 않았습니다.

- 훅과 컴포넌트의 분리 기준, 파일 위치, 중복 처리 기준 부재
- `components`·`hooks` 같은 역할 단위 폴더 — 만들기는 쉬우나 그 훅이 어디서 왜 쓰이는지 드러나지 않음
- 같은 목적의 코드가 여러 곳에 분산
- 폴더 구조를 여러 번 바꿨으나 기준이 없어 곧 원형으로 회귀

### 해결 — 구조·패턴을 함께 정리

구독제 전환으로 기존 로직과 분리된 기능을 새로 시작할 기회가 생겨, 팀과 공감대를 이룬 뒤 FSD를 도입했습니다.

- **FSD 레이어 규칙 정립** — 폴더 역할과 도메인 데이터 분리, `{Domain}API` + query key factory, DTO와 도메인을 잇는 mapper 분리
- **Compound Component·Render Props로 관심사 분리** — 단점(Context 리렌더 비용, "커스텀 훅과 props로도 가능")까지 함께 기록하고 관심사 분리가 목적일 때만 적용하는 기준 수립
- **서버·클라이언트 상태 분리 컨벤션**을 팀 규칙으로 정의 (TanStack Query 데이터를 useState로 복제하지 않기 등)

적용 사례는 둘입니다. 3개 앱에 중복되던 CaseInfo 다이얼로그를 Compound + FormProvider 단일 컴포넌트로 추출해 약 66%(984→330줄) 줄였고, 통신 방식(Custom Protocol과 HTTP)은 나중에 한쪽으로 굳히기 쉽도록 전환 지점만 추상화하되 약간의 중복은 의도적으로 허용했습니다.

![패턴을 고르는 사다리와 실전 적용 — 관심사 분리가 필요한 만큼만 쓰고, 도입의 전제를 배웠다](../../images/portfolio/diagrams/design-patterns.svg){.diagram}

### 회고

한계가 분명했습니다. FSD를 도입했는데도 `widgets`·`pages`처럼 UI 단위가 레이어에 섞여 "이 파일을 어디 넣을지"가 풀리지 않았고, 그걸 정하느라 작은 논의가 이어졌습니다. 디자인 패턴도 "코드 일관성"이라는 명분으로 굳이 필요하지 않은 곳에 적용한 경우가 많았고, 제안한 방향을 팀원들이 다르게 이해해 같은 패턴을 쓰는 방법이 갈라지기도 했습니다. 가장 크게 깨달은 것은 디자인 패턴이 어떤 문제를 푸는지 정확히 이해하지 못한 채 도입했다는 점입니다.

그래서 지금은 기술을 도입할 때 우선순위 높은 문제를 먼저 정의하고, 대안을 비교해 맞을 때만 팀이 같은 이해를 가진 상태에서 도입합니다. 효용만이 아니라 도입 비용(커뮤니케이션·마이그레이션·과도기 복잡도)까지 따져야 한다는 것도 이때 배웠습니다. 구조 자체가 나빴던 것은 아닙니다 — 그 코드는 모노레포로 옮겨간 뒤에도 남아 있습니다. 배운 것은 '좋은 구조'가 아니라 '도입의 전제'였습니다.

## 케이스 목록 썸네일 로딩 최적화 — 지연 로딩·요청 배치·실패 캐싱

`2025.10 ~ 2026.06` · `React · TanStack Query · IntersectionObserver · Context API`

> **성과** — 운영 중 발생한 무한 재요청 회귀를 공유 캐시 구조로 근절(재마운트돼도 중복 요청 없음을 회귀 테스트로 고정), 썸네일을 지연 로딩과 요청 배치로 최적화해 "N장 = N요청" 구조를 해소

### 문제

케이스 목록은 사용자가 가장 자주 보는 화면이고 썸네일이 수십 장 표시됩니다.

- "N장 = 네트워크 N요청"이 되기 쉬운 구조
- 운영 중 깜빡임과 무한 재요청 발생
- 원인 — 카드가 재마운트될 때마다 훅이 새로 생겨 같은 썸네일을 중복 요청
- 403 같은 영구 오류도 새 URL로 계속 재요청

### 해결

- **IntersectionObserver로 viewport에 들어온 썸네일만 로드**하고, 50ms 윈도우 안의 요청을 모아 한 번에 배치 요청하는 공통 훅(Context Provider 기반) 구현
- **캐시를 카드 바깥 Provider로 끌어올려 모든 카드가 공유** — 재마운트에도 캐시 유지
- **성공(4분)뿐 아니라 실패(10초)도 캐시** — 영구 오류를 짧게 기억해 재마운트 시 네트워크 재호출 없이 즉시 "No data" 처리
- 단일 마운트 안의 `onError` 폭주를 억제하는 재시도 1회 제한을 보조 장치로 배치, **성공 시 실패 횟수를 초기화하면 같은 영구 오류가 반복되므로 의도적으로 초기화하지 않음**
- 깜빡임은 로딩 상태를 첫 요청에만 토글하고 재시도는 silent로 처리해 제거
- 회귀 테스트로 "같은 Provider 안에서 재마운트돼도 중복 요청 없음" 검증

![케이스 목록 썸네일 — 보일 때만 로드하고, 모아서 한 번에, 실패도 캐시한다](../../images/portfolio/diagrams/list-performance.svg){.diagram}

### 회고

무한 재요청은 재시도 횟수만 제한해도 멈춥니다. 하지만 그것은 증상이고, 진짜 원인은 재마운트마다 훅이 새로 생겨 캐시가 소실되고 같은 오류를 다시 호출하는 구조였습니다. 재마운트 자체를 없애는 것은 더 큰 공사라 공유 캐시로 우회하는 실용적 선택을 했습니다 — 증상을 덮을지 구조를 고칠지 사이에서 비용 대비 효과가 가장 큰 지점을 고른 작업입니다.

설계에서 하나 더 신경 쓴 것은 실패를 다루는 방식입니다. 보통 캐시는 성공만 담지만 여기서는 403 같은 영구 오류도 짧게 캐시했습니다. 실패를 기억하지 않으면 재마운트마다 같은 오류를 다시 호출하기 때문입니다.

## 프론트엔드 모노레포 통합 — 레포·환경 구성 일원화

`2024.06 ~` · `TypeScript · NX · Git Subtree · i18n`

> **성과** — 조직 변경에 맞춰 앱 2종·라이브러리 6종을 커밋 이력 보존하며 NX 모노레포로 이관하고, 버전이 어긋나던 공용 라이브러리를 빌드타임에 합쳐 통합 배포·버전 정합을 확보, 잔존 설정이 유발하던 OOM도 진단해 빌드 태스크 11→9로 정리

### 문제

분리됐던 팀들이 합쳐지는 조직 변경이 있었고, 레포 구조가 그 변화와 맞지 않았습니다.

- 각자 관리하던 레포가 떨어져 있어 하나의 변경이 여러 PR·여러 배포로 분리
- 공용 라이브러리는 앱마다 버전이 어긋나 배포 시점 조율과 팀 간 커뮤니케이션 비용 발생
- 환경별 URL·도메인 구성이 서비스마다 다르게 구성
- 다국어 관리도 중복 업로드와 분산 스크립트로 파편화

### 해결

- **NX 유지 + OOM 해소** — 모노레포 도구를 새로 고르는 대신 기존 NX 유지(전환 이득이 이관·재학습 비용을 넘지 못한다고 판단). 잔존하던 `webpack.config.js`가 NX 자동 타겟 추론을 유발해 불필요한 산출물과 OOM을 일으키던 것을 진단해 **빌드 태스크 11개 → 9개, OOM 해소**
- **Git Subtree로 이관** — 별도 레포의 클라이언트 앱 2종·공용 라이브러리 6종을 메인 모노레포로 이관. 단순 복사가 아니라 **커밋 이력을 보존**하고 네임스페이스 충돌은 리네임으로 해소
- **도메인 통합 라이브러리** — 환경별로 분산된 도메인·URL 구성을 단일 라이브러리로 일원화. 기준 도메인 하나에서 backend·gateway·테넌트 호스트가 파생되고, 통합 도메인에서는 상대 경로, 레거시에서는 환경변수 기반 절대 URL로 갈라지되 호출부는 하나의 형태로 통일
- **다국어 중앙화** — 중복 업로드 89줄과 14개 스크립트로 분산된 i18n 관리를 단일 스크립트로 통합

![모노레포 통합 전/후 — 분산된 레포들이 단일 NX 모노레포와 도메인 통합 라이브러리 위로 모인다](../../images/portfolio/diagrams/monorepo.svg){.diagram}

### 회고

분산됐던 레포를 하나로 합치니 여러 곳에 걸친 변경을 한 PR에서 한눈에 보고 리뷰할 수 있게 됐습니다. npm 패키지나 외부 모듈로 따로 배포되며 버전이 어긋나 생기던 불일치도 빌드 타임에 함께 컴파일하는 방식으로 사라졌습니다.

"무엇을 합칠까"보다 합친 뒤에도 흔들리지 않을 토대 — 도메인 통합 라이브러리 — 를 먼저 마련한 것이 다음 단계인 격리 재현 환경의 기반이 됐습니다.

## B2B 구독·결제 프론트엔드 — 예측 가능/불가능 에러 분리

`2023.09 ~ 2025.07` · `React · TypeScript · TanStack Query`

> **성과** — 모든 에러를 한 덩어리로 처리하던 구조를 예측 가능/불가능 에러로 분리해, 한 기능의 실패가 전체 페이지를 중단시키지 않도록 개선(BusinessLogicError·ErrorBoundary 체계는 모노레포 이관 후에도 존속)

### 문제

일회성 크레딧에서 반복 구독으로 전환하는 시점에 구독·결제 화면(플랜 업그레이드·좌석 구매·취소·재개·쿠폰·결제수단·히스토리)을 전담했습니다. 당시 조직에는 에러 처리 정의가 없었습니다.

- 모든 에러를 하나의 unknown으로 일괄 처리 — 예측 가능·불가능 구분 없음
- 한 기능에서 발생한 에러가 전체 페이지를 에러 화면으로 전환
- 케이스 목록 조회 1회 실패로 SNB·대시보드 접근까지 차단
- 원인 — 서버가 의도적으로 내려준 비즈니스 에러와 예상하지 못한 시스템 실패를 구분하지 않은 구조

### 해결 — 에러를 둘로 나누다

- **예측 불가능한 에러는 ErrorBoundary로 격리** — 컴포넌트마다 분산된 명령형 방어 코드를 대체하고, 실패 허용 범위를 도메인 의존 관계로 구분
- billing 정보를 받지 못해도 **결제 내역 조회·구독 취소·뒤로가기는 동작 유지**
- **예측 가능한 에러는 코드별 분기** — 서버가 `HTTP 200 · success:false · errorCode`로 내려주는 비즈니스 에러는 실패가 아니라 의도된 결과이므로 폴백 UI로 뭉뚱그리지 않음
- `BusinessLogicError` 커스텀 클래스로 throw하고 `.when(errorCode, action).otherwise()` 체인으로 분기
- 결제 상태는 **서버·Stripe 동기화 기준**으로 두고, 무한 반복 방지 폴링과 origin이 격리된 결제 팝업으로 외부 연동 실패에 대비

![이중 에러 처리 — 예측 불가능한 에러는 ErrorBoundary로 기능 단위 격리, 예측 가능한 비즈니스 에러는 코드별 분기](../../images/portfolio/diagrams/dual-error-handling.svg){.diagram}

### 회고

에러 처리의 출발점은 정교한 도구가 아니라 에러를 구분 짓는 일이었습니다. 예측 가능한 실패와 불가능한 실패를 나누지 않으면 잘 만든 ErrorBoundary를 두어도 결국 같은 폴백으로 처리됩니다. 이 구조는 모노레포로 이관된 뒤에도 `BusinessLogicError`와 `withErrorBoundary` HOC로 남아 있습니다.

다만 조직 차원의 에러 처리 정의는 여전히 없고, 무엇이 실패해도 무엇은 살아남아야 하는가를 결제 데이터 의존 관계까지 끊어내는 설계는 당시 출시 우선순위와 설계 역량의 한계로 끝까지 가지 못했습니다. 이 문제의식은 이후 관측·복원력 표준화에서 조직 차원으로 이어갔습니다. 에러 응답 형식을 서버가 HTTP 200에 success:false로 내려줄지 4xx·5xx로 내려줄지부터 합의가 필요했다는 점에서, 에러 처리는 프론트엔드 혼자 정할 수 없고 서버와의 계약이 전제라는 것도 확인했습니다.

## 웹·로컬 CAM 연동 Electron 데스크톱 앱 — Dentbird Linker

`2024.07 ~ 2025.12, 이후 단독 운영` · `Electron · React · TypeScript · Datadog`

> **성과** — 좌표계·전달 방식이 제각각인 외부 CAM 12종을 단일 연동 인터페이스로 통합, 앱마다 다르던 설치 감지 타임아웃을 3초로 맞추고 비차단 안내로 통일, Windows 전용 CAM을 Mac에서 재현하는 검증 도구로 원인을 우리 쪽과 CAM 쪽으로 구분

![Dentbird Linker와 검증용 Mock Server — 외부 CAM 12종(포트 연동 4종 + 프로세스 실행 8종)을 한 인터페이스로 추상화한 연동 화면(좌)과, CAM 없이 연동·자동 업데이트를 시나리오별로 재현해 검증한 Mock Server(우)](../../images/portfolio/screenshots/linker-mockserver.png)

### 문제

Dentbird에서 디자인한 보철 케이스를 사용자 PC의 외부 CAM 소프트웨어로 보내는 사내 연동 앱을 단독 설계·운영했습니다. 연동은 파일을 전달하는 **데이터 채널**과 앱 설치·실행 여부를 아는 **감지 채널** 두 축으로 나뉘고, 이 케이스는 둘을 모두 다룹니다.

- 기존에는 다운로드 → 압축 해제 → 수동 투입을 거쳐야 했음
- 자체 로컬 서버가 없는 CAM은 연동 자체가 불가능
- Chrome의 **LNA(Local Network Access)** 정책이 웹에서 로컬로 가는 통신을 차단하며 권한 팝업을 놓친 사용자의 CS 문의 증가
- "지금 되는 방법"을 고르면 정책이 강화될 때 다시 막히는 구조

### 해결 — 대안 비교 후 장기 안정성 기준 선택

여러 통신 방식을 구현 속도가 아니라 **장기 안정성** 기준으로 비교했습니다.

| 방안 | 검토 결과 |
|------|-----------|
| WebSocket 로컬 서버 | 구현은 가장 빠르나 곧 LNA 적용 대상 → 1~2년 후 재차단될 단기 해법, **탈락** |
| HTTPS 로컬 서버 | 인증서·배포 부담 + 같은 LNA 사정 → **탈락** |
| **Custom Protocol** | HTTP 요청이 아니라 LNA 적용 대상이 아님 → **채택** |

- Custom Protocol을 **중간 레이어**로 두어, 브라우저가 프로토콜로 Linker를 실행하며 세션 정보를 넘기면 Linker가 서버에서 파일을 직접 받아 변환 후 CAM을 실행하는 구조로 재설계
- 좌표계·전달 방식이 서로 다른 **외부 CAM 12종**(프로세스 실행 8종 + 포트 연동 4종)을 하나의 변환·연동 인터페이스로 추상화

![Linker 통신 구조 — 브라우저가 Custom Protocol로 Linker를 깨우고, Linker가 파일을 받아 변환 후 CAM에 투입한다](../../images/portfolio/diagrams/linker-flow.svg){.diagram}

- 운영 중 발생하던 정체불명의 'unknown error' 모달은 **처음 의심한 요청 페이로드 문제가 아니라는 것을 Datadog 로그 순서로 확인**하고, 실제 원인이 변환 대상에 잘못 섞여 들어간 point cloud 파일임을 로그로 확정
- 명세가 없던 외부 export는 **기존 동작 자체를 명세로 고정** — CAM으로 보내는 시점의 STL byte snapshot(크기·sha256)을 기록해 특성화(characterization) 테스트로 고정한 뒤 구현을 그 테스트에 통과시키는 방식으로 재구현
- CAM 12종을 설치하지 않고도 검증하도록 **Mock Server 구현** — 헬스체크·파일 핑 엔드포인트와 자동 업데이트 응답을 재현하고, 성공·에러(500)·지연·타임아웃·부분 실패 시나리오를 버튼으로 전환

### 재현할 수 없는 환경을 재현 가능하게 — 외부 CAM 진단

연동한 CAM 중 하나에서 보철 가장자리(마진)가 물결처럼 어긋나 들어가는 문제가 접수됐습니다. 이 CAM은 Windows 전용이고 3D 뷰포트가 GPU 렌더라 Mac에서는 결과를 볼 수 없었습니다.

- Windows 빌드머신에 원격으로 접속해 **Linker가 실제로 보내는 것과 같은 요청·같은 변환 규칙으로 전송을 재현하는 도구**를 만들고 팀이 쓸 수 있게 스킬로 등록
- 조건을 **하나씩만 바꿔 대조** — 함께 보내는 마진 정보의 유무, 보철 종류 값 변경
- 확인 결과 이 CAM은 전달받은 마진 정보를 쓰지 않고 항상 형상에서 직접 검출하며, **그 검출 방식을 보철 종류 값이 선택**. 임플란트 케이스에 자연치용 값이 들어가 있던 것이 원인
- 그 전까지 내린 "CAM 쪽 문제라 고칠 수 없다"는 결론은 테스트용 특이 케이스를 일반화한 것이었고, 실제 QA 케이스로 다시 재현해 정정
- 반대 방향의 문의("여러 개를 보냈는데 하나만 열린다")는 코드를 전수 확인한 뒤 우리 전송은 정상이고 해당 CAM의 실행 인자가 마지막 하나만 받는다는 것을 사내 벤더 문서에서 확인해 **결함이 아님을 근거와 함께 확정**

### 설치 감지 — 감지를 믿지 않는 방향으로

두 번째 축인 감지 채널입니다. 브라우저는 LNA 정책 때문에 로컬 헬스체크로 앱 실행을 직접 확인할 수 없어, 창 포커스 변화 같은 휴리스틱으로 추정할 수밖에 없습니다. 두 방향의 오탐이 있었습니다.

- **false-negative** — 앱이 이미 실행 중이면 OS가 기존 창으로 라우팅해 포커스 변화가 없어 '미설치'로 오인 → 설치돼 있는데 설치 모달 표시
- **false-positive** — 로딩 중 사용자가 DevTools를 열어 포커스가 빠지면 '설치됨'으로 오인 → 미설치인데 다운로드 안내 억제

- 감지를 완벽하게 만들지 않고 **틀려도 사용자가 막히지 않는** 쪽으로 정책 통일
- batch 2.5초·Linker 10초로 달랐던 감지 타임아웃을 **3초로 일치**시키고, 미감지면 미설치로 간주하되 **설치 안내를 항상 비차단(non-trapping)으로 표시**해 어떤 경우에도 다운로드가 가능하게 함
- DevTools로 인한 false-positive는 타임아웃으로 막지 못하는 한계임을 **인지한 채 수용**

![설치 감지 정책 — 감지를 분기 조건이 아니라 보조 신호로 두고, 실행과 다운로드 두 경로를 항상 열어 둔다](../../images/portfolio/diagrams/deeplink-detect.svg){.diagram}

근본 해법으로는 Zoom·Slack 같은 설치형 서비스처럼 **감지 판정 자체를 없애고 다운로드 안내를 항상 제공하되 설치돼 있으면 자동 실행되는 방식**을 제안해 기획·QA와 합의했고, 아직 착수 전입니다.

### 회고

처음엔 로컬 서버 방식이 핵심이었지만 정책 변화로 더는 쓸 수 없게 됐고, 직접 폐기한 뒤 Custom Protocol 기반으로 옮겼습니다. "당장 되는 방법"이 아니라 "정책이 또 바뀌어도 흔들리지 않는 방법"을 고른 판단이 이 프로젝트의 핵심이었습니다. 브라우저·OS의 실행환경 정책(LNA, 포커스, 프로토콜 핸들러)이 웹과 로컬의 경계에서 무엇을 막고 허용하는지를 이 과정에서 깊이 이해했습니다.

감지에서도 같은 태도를 얻었습니다. 휴리스틱은 늘 틀릴 수 있으므로, 감지를 완벽하게 만들려 애쓰기보다 틀려도 사용자가 막히지 않도록 설계하는 쪽이 더 단단했습니다. 감지 판정 자체를 없애는 방향까지 제안하게 된 것은, 휴리스틱 위에 보강을 더하는 방식으로는 구조적 한계를 넘지 못한다는 것을 같은 문제가 다시 열리며 겪었기 때문입니다.

## Medit 소프트웨어 연동 인앱 현대화 — 방치된 통합을 되살리고 결합을 끊다

`2026.07` · `Electron · TypeScript · MUI`

> **성과** — 곧 사용이 끊길 뻔한 협력사 인앱을 엔진·로그인·의존 정리로 되살리고, 우리 서비스가 바뀌어도 재빌드가 필요 없는 구조로 전환 (실제 Electron과 CDP로 검증 완료, 배포 대기)

### 문제

협력사 Medit의 소프트웨어 안에서 Dentbird를 쓸 수 있도록 Electron 인앱 형태로 제공했지만 2023년 이후 유지보수되지 않았습니다.

- 그사이 우리 서비스는 인앱을 고려하지 않고 업데이트를 거듭
- 로그인 후 재진입 시 엉뚱한 페이지로 이동, 미로그인 상태에서 작업 저장 실패
- 곧 배포될 버전에서는 인앱에서 서비스를 아예 사용할 수 없는 상황

### 해결

- 최신 3D 엔진이 요구하는 WASM 기능(JSPI)이 구버전에서 동작하지 않아 **Electron 25를 31로 업그레이드**해 재빌드
- 로그인 문제의 원인은 인앱이 우리 서비스 내부 방식에 불필요하게 결합돼 있던 것 — 과거 인앱은 유저 정보 API(`get-user`) 응답이 200이면 로그인 성공으로 판단했고, 이 API를 레거시로 제거하자 판단이 무너짐
- 급한 대로 해당 경로에 같은 이름의 이미지를 항상 내려주는 임시 대응을 한 뒤, **확인할 필요도 없던 결합을 IPC 기반 흐름으로 재설계해 제거**
- 회사 UI 라이브러리 의존을 **MUI로 대체** — 해당 라이브러리는 패키지가 GitHub으로 이전되며 설치 경로도 사라진 상태였음
- 브라우저 stub 검증이 불안정해 **실제 Electron에 CDP로 접속해 3D 엔진 구동까지 확인**

### 회고

인앱은 C++ 애드인과 함께 빌드되는 구조라 재빌드 자체가 부담이었습니다. 그래서 되살리면서 우리 쪽 구현과의 결합을 줄여, 이제는 서비스의 구현 아키텍처가 바뀌지 않는 한 인앱을 다시 빌드할 일이 없습니다. 결합을 완전히 없애는 데 집착하기보다, 큰 변경이 있을 때만 드물게 재빌드하면 되는 선까지 끊는 것을 택했습니다.

두 문제는 해결됐고, 릴리스는 협력사 Medit이 맡아 배포를 기다리고 있습니다.
