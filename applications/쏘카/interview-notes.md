## 강점 — 면접에서 전면에

- ★★ **AI 에이전트의 한계를 측정해 본 경험**. 공고 문구가 "작동 방식·강점·한계를 체득하고 자기 워크플로우의 일부로"인데, 이건 자랑거리 나열이 아니라 **되돌린 경험을 말하라는 요구**로 읽는 게 맞음. 명세 검증 전량 자동화 → 비결정성·토큰 비용으로 회수 → 격리 재현 위 E2E, 그리고 mutation testing(코어 라이브러리 57%)으로 "AI가 만든 걸 AI가 평가하는" 구조의 맹점을 수치로 확인 → CFR로 측정 축 전환.
- ★★ **쏘카의 결론과 독립적으로 같은 지점에 도달**. 쏘카 블로그(2026.07.22)는 "AI를 작게 가두고 코드가 워크플로우·안전성·제어를 담당", "에이전트는 절대 코드를 배포하지 않는다"로 끝남. 본인도 AI를 판단 단계에만 결합하고 결정성은 격리 환경·E2E 코드로 확보. **면접에서 이 글을 읽었다고 말하고 자기 사례와 대조하면 대화가 가장 잘 붙는 지점.**
- ★★ **한 문제를 End-to-End로 소유** — Linker 0→1 단독 설계·구현·운영(+검증용 Mock Server 자작), CFR 대시보드를 화면부터 API까지, 기업 랜딩 v3 풀스택 단독. 공고의 "정의 → 구현 → 출시 → 결과 학습"에 그대로 대응.
- ★★ **반복 작업을 도구·스킬로** (공고 담당 업무의 마지막 항목, 대부분의 지원자가 근거를 못 대는 자리) — Windows 전용 CAM을 Mac에서 실제 전송과 똑같이 재현하는 원격 도구를 만들어 **Claude 스킬로 등록**해 팀이 같은 명령으로 재현·캡처. Mock Server, 디버깅 방법론 문서까지 같은 계열.
- ★ **결제·외부 연동 예외 처리** — 우대 도메인 '결제'. 서버·Stripe 동기화 기준, 무한 반복 방지 폴링, origin 격리 팝업, 예측 가능/불가능 에러 분리.
- ★ **자기 결론을 스스로 뒤집은 사례** (쏘카 "본질과 맥락을 먼저 파악" 컬처와 직결) — 외부 CAM 마진 문제를 "CAM 쪽 문제라 우리가 못 고친다"로 결론 냈다가, 테스트용 특이 케이스를 일반화한 것임을 실제 QA 케이스 재현으로 확인하고 정정. 원인은 보철 종류 값이었고 우리 쪽에서 고쳤음.
- ★ **기존 방식을 의심하고 바꾼 사례** — LNA 대응(당장 되는 WebSocket 탈락), 설치 감지를 '정확도 높이기'가 아니라 '틀려도 막히지 않게'로 전환, 빌드·서명을 담당자 PC·인프라팀 USB 의존에서 빌드머신 단독 운영으로.

## 약점 항목과 답변 프레임

### 백엔드 프로덕션 깊이 (자격 — 가장 중요)
- 자격은 "백엔드·프론트엔드 **어느 한 축**"이라 프론트로 충족. 다만 직무 정의가 전 스택 소유라 반드시 파고들 항목.
- 인접 근거: 기업 랜딩 v3 **Fastify + MongoDB 서버 API까지 단독**(2년+ 운영), CFR 대시보드 **API 직접 구현**, Linker의 로컬 서버·프로토콜 핸들러·파일 변환 파이프라인(Node/Electron 메인 프로세스), 격리 재현 환경에서 **서버·DB를 컨테이너로 함께 띄워 운영**, 원격 빌드머신에 접속해 도구를 배포·실행하는 스크립트 작성.
- 답변: "제품 트래픽을 받는 대규모 서버를 운영해 본 적은 없습니다. 다만 화면만 만든 적도 없습니다 — 랜딩은 서버 API까지, CFR 대시보드는 데이터 수집·API까지 직접 만들었고, 격리 환경을 만들며 서버·DB 구성까지 다뤘습니다. 프론트가 주축이지만 필요하면 서버로 넘어가서 끝내는 방식으로 일해 왔습니다." **과장 금지 — "백엔드도 프로덕션 수준"이라고 말하지 말 것.**

### 데이터 분석 / SQL (담당 업무)
- 공고: "데이터를 뽑아야 하면 SQL을 쓰고". 본인은 SQL 실무 비중 낮음. **여기는 정직하게 미달로 두는 게 맞음.**
- 인접 근거(측정으로 결정을 바꾼 사례): ① mutation score로 테스트 유효성 측정 ② CFR을 단순 건수가 아니라 **심각도·관리 한계·재발 결함**으로 설계 ③ i18n 버그를 **직접 집계해** 도입하려던 타입 체크가 가장 흔한 유형을 못 막는다는 걸 확인하고 방향 변경 ④ 클라이언트 4개 앱의 빌드 시간·번들·타입체크를 조건 고정해 측정하고 **빌드 개선은 불필요로 판정**, 병목이 초기 로드 페이로드임을 특정(2026-07) ⑤ 썸네일 엔진 통합 제안에 **번들 감소 0**임을 확인해 보류.
- 답변: "쿼리를 짜서 분석하는 비중은 낮았습니다. 대신 무엇을 재야 판단이 바뀌는지를 정하는 일은 계속 해왔습니다. 최근에도 빌드가 느리다는 이야기가 있어서 네 개 앱을 측정했는데, 빌드는 손댈 필요가 없고 초기 로드 크기가 문제라는 결과가 나와서 방향을 바꿨습니다." → **"안 해도 된다"를 데이터로 말한 사례가 가장 잘 먹힘.**

### 모빌리티·주차·오프라인 도메인 (우대)
- 전부 미경험. 다만 **오프라인·외부 시스템에 물린 예외 처리**는 Linker가 정확히 그 성격: 사용자 PC에 설치된 CAM 12종, OS 프로토콜 핸들러, 브라우저 정책, 설치 여부를 확신할 수 없는 상태에서의 UX 설계.
- 답변: "차량·주차 도메인은 처음입니다. 다만 '내 코드 밖에서 벌어지는 일이 그대로 실패로 돌아오는' 환경은 계속 다뤘습니다. 사용자 PC의 외부 소프트웨어 12종, 브라우저 정책 변경, 결제사 상태 — 감지가 틀릴 수 있다는 전제에서 UX를 설계한 경험이 그쪽 도메인과 닿는 부분이라고 봅니다."

### 기능 정의 단계 참여 / PM·디자이너 협업 (자격)
- 근거는 있으나 규모가 작음. 발명 금지 — 있는 것만: ① 설치 감지 정책 통일과 **감지 판정 자체를 없애는 2단계 방향을 직접 제안해 기획·QA와 합의**, ② 3D 썸네일 Three.js 통합 제안에 대해 **번들 감소가 0임을 확인하고 "안 하는 게 낫다"를 데이터로 정당화**, ③ 3D 뷰어 부분 실패 시 살아있는 mesh만 렌더하는 방향 제안(착수 전).
- 답변: "기획서를 받아서 구현만 한 적은 별로 없습니다. 다만 제품 기획을 주도한 경험이라기보다, **어떻게 풀지와 하지 말지를 제안한 쪽**에 가깝습니다." 솔직하게 규모를 인정하고, 판단 근거의 질로 대체.

### 0 → 1 제품 출시 (우대)
- Linker(사내 제품, 0→1 단독), Mock Server, CFR 대시보드, 기업 랜딩 v3는 모두 0→1. 다만 **사외 고객 대상 신규 서비스 런칭**은 아님 — 사내·B2B 성격임을 밝힐 것.

### 경력 3년 (우대)
- 2023.09~ 현재 2년 11개월. **지원 자격이 경력 무관**이라 컷 사유는 아님. 물으면 사실만.

### 에이전트 인프라 구축 (LangGraph·MCP 서버·지식 그래프)
- 쏘카는 LangGraph·Playwright MCP·Neo4j로 **에이전트 시스템 자체를 만드는** 단계. 본인은 에이전트를 **운용·검증**하는 쪽(Claude Code 상시 운용, Playwright MCP 사용 후 비결정성 때문에 폐기, 자작 TC-Verify는 Planner·Verifier 2단 구성).
- 답변: "프레임워크로 에이전트 시스템을 구축해 본 경험은 없습니다. 대신 에이전트에 무엇을 맡기면 안 되는지를 실패로 배운 쪽입니다 — Playwright MCP로 브라우저를 직접 조작하게 했을 때 실행마다 결과가 달라지는 문제를 겪고 결정성을 코드로 가져왔습니다." → 쏘카 블로그의 "워크플로우는 코드가 고정" 결론과 정확히 같은 이야기.

## 예상 질문

1. **"AI 에이전트가 잘 동작하는 조건과 한계를 설명해보세요"** — 공고 문구 그대로 나올 가능성 높음. 조건: 검증 가능한 출력·좁은 판단 범위·결정성이 코드 쪽에 있을 것. 한계: 비결정성, 자기 산출물 자기 평가, 맥락 부재(티켓 코멘트 사례).
2. mutation score 57%를 확인한 뒤 무엇을 바꿨나 → 테스트를 더 만드는 대신 **측정 축을 CFR로 옮긴 이유**.
3. Custom Protocol 선택 근거와 지금도 유효한가 → LNA 적용 범위, WebSocket을 탈락시킨 기준.
4. 한 기능을 정의부터 출시까지 소유한 사례 → Linker 또는 CFR 대시보드.
5. 백엔드는 어디까지 해봤나 → 위 프레임대로, 과장 없이.
6. 쏘카에서 무엇을 하고 싶은가 → AI가 만든 변경을 안전하게 내보내는 검증 축. 단 **직무는 제품 오너십**이므로 "품질 인프라만 하고 싶다"로 읽히지 않게 주의 — 제품 기능을 소유하면서 그 검증까지 함께 만든다는 프레임으로.
7. **"반복되는 작업을 스킬·자동화로 만든 적 있나"** (공고 담당 업무에 명시) → 원격 CAM 재현 도구를 스킬로 등록한 사례. 왜 스킬까지 갔는지(팀원이 같은 명령으로 재현·캡처하게)를 함께.
8. **"결론이 틀렸던 경험"** → 외부 CAM 마진 원인을 벤더 문제로 확정했다가 실제 QA 케이스 재현으로 뒤집은 사례. 무엇을 일반화해서 틀렸는지까지.
9. 팀에 AI 도구를 어떻게 퍼뜨렸나 → 스킬 등록·문서화(디버깅 방법론) 수준. **전사 도입을 주도한 적은 없음 — 과장 금지.**

## 전략 메모

- 이 공고는 **AI가 자격 요건**인 드문 케이스. 다른 회사 파생에서는 차별점이었지만 여기서는 기본 요건이므로, **깊이(한계·측정)로 변별**해야 함.
- 서류에서는 약점을 적지 않되, 면접에서 물으면 위 프레임으로 정직하게. 쏘카는 "본질과 맥락을 먼저 파악" / "백그라운드보다 역량"이 명시된 조직이라 정직한 미달 인정이 감점보다 신뢰로 갈 확률이 높음.
- ★ 주의: 공고 본문의 "화면 너머의 모든 일이 그대로 코드의 책임" 같은 표현을 그대로 되받아 쓰지 말 것 (이 레포에서 폐기한 멋부림 프레임과 같은 어투). 자기 사례의 사실로 말할 것.
