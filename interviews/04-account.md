## 1. WHY — 문제 실체

**Q1. 왜 FSD·디자인 패턴·에러처리·테스트를 본격 도입하려 했나요?**

(요지) 클라이언트 코드가 구조 기준 없이 커지면서 — 응집도는 낮고 결합도는 높아, 요구사항이 바뀌면 어느 파일을 고쳐야 할지, 고치면 어디에 사이드이펙트가 생길지 장담할 수 없었다. 도메인 정의가 없어 문제 구조가 한눈에 안 들어왔고, 앱 서비스 로직과 비즈니스 로직이 혼재했다. 에러 처리도 제대로 정의돼 있지 않아, 한 기능에서 난 에러가 전체 페이지를 에러 화면으로 바꾸고 모든 걸 unknown 에러로 처리하는 경우가 많았다. (출처: Confluence "FSD", "선언적 에러 처리")

---

## 2. HOW — 트레이드오프

**Q2. 어떻게 풀었나요? 어떤 패턴·구조를 택했나요?**

(요지)
- **FSD**로 폴더 역할을 명확히 하고 도메인 데이터를 분리. API는 `{Domain}API` 객체 + react-query query key factory, DTO↔도메인 객체를 mapper로 분리하는 규칙을 직접 정립.
- **Compound Component / Render Props**로 컴포넌트 관심사 분리(MobileHeader, SeatCounter). 각 패턴의 단점(Context 리렌더, "커스텀훅+props로도 가능")도 문서에 함께 기록.
- **ErrorBoundary**로 명령형 `if(!data) return null` 방어 코드를 선언적으로 전환하고, **Fault Tolerance**(billing 정보 못 받아도 결제내역·구독취소·뒤로가기는 살림)를 도메인 의존 관계 기준으로 구분.
- **BusinessLogicError** 커스텀 클래스로 `statusCode:200 / success:false / errorCode` 서버 응답을 throw, `.when(errorCode).otherwise()` 체인으로 분기.
- **테스트**는 TDD를 강제하지 않고 목적에 맞게, msw로 서버 모킹 + describe-context-it 구조화.

**Q2-후속. 돌아보면 이 선택들에 어떤 문제가 있었나요? (트레이드오프)**

(사용자 원문 취지)
- FSD를 도입했지만 **명확한 폴더 구조 기준이 없는 느낌**이었다. 어떤 파일을 만들 때 **위치 고민 없이 만들 수 있어야 좋은 구조**라고 생각하는데, 실제로는 **매번 어디에 넣어야 하는지 상의하는 시간이 많았다.**
- 디자인 패턴은 **굳이 적용 안 해도 되는 곳에 "코드 일관성"을 위해 적용한 부분이 많았다.** 게다가 **내가 제안한 방향을 팀원들이 잘못 이해해서, 같은 패턴인데도 사용하는 방법이 다른 경우**가 많았다.
- 가장 크게 깨달은 것: **디자인 패턴을 도입하려는 목적을 정확히 했어야 했는데 그러지 못했다.** 디자인 패턴이 **풀려는 문제를 이해하지 못한 채 도입**한 것. "일관되지 않은 코드 구조"를 고민하며 제안했지만, 사실 디자인 패턴이란 건 **오랜 기간 내려온 공통적인 문제를 해결하는 패턴**인데, 나는 그런 문제를 풀려고 도입한 게 아니었다.
- 그래서 결론은: **어떤 기술을 도입할 때는 항상 문제를 해결하는 게 우선**이고, 하나의 기술이 여러 문제를 풀 수 있더라도 **우선순위가 높은 문제를 해결하는 게 가장 좋다.**

## 3. RESULT — 결과

**Q3. 실제로 무엇이 나아졌나요? 지표가 있나요?**

(요지) 정량 지표(커버리지%·버그 감소율)는 남아 있지 않음 — **추정/창작하지 않음.** 대신:
- 에러 처리가 "전체 페이지 에러화 / unknown 일괄 처리"에서 **기능 단위 fallback + 비즈니스 에러 코드별 분기**로 정리됨. (코드로 확인: ErrorBoundary 6곳, BusinessLogicError 클래스)
- 구독/시트/빌링 도메인에 **테스트 32개**가 붙어, 이 도메인이 본인의 첫 테스트 코드 자산이 됨.
- 구독제 전환에 필요한 신규 FE(플랜 업그레이드·시트 구매·구독 취소/재개·쿠폰·결제수단·결제내역)를 **전담 구현**.

**Q3-후속. 누가 효과를 봤나요?**

(보강 필요 시 인터뷰) 일차적으로 본인·후속 유지보수자(에러/구조 정리). 사용자 측은 구독제 자체의 가치. — 정량 없음.

## 4. 지속성·한계 — 성장 서사 ★

**Q4. 지금도 유지되나요?**

(요지) 구 레포 → `dentbird-solutions` 모노레포로 이관되며 **FSD는 전면 적용으로, BusinessLogicError·withErrorBoundary HOC·msw 핸들러도 그대로 정착**(코드로 확인). 즉 한계를 느꼈지만 **구조 자체는 살아남았다.** 마이그레이션은 팀 단위로 진행, 본인도 여러 앱을 옮김.

**Q4-후속. 다시 한다면 무엇을 다르게?**

(사용자 원문 취지)
- "좋은 경험이었고, **좋은 형태의 코드라는 생각은 지금도 변함없다.**" 구조나 패턴 자체를 부정하는 게 아니다.
- 다만 **이런 패턴·설계를 도입하려면 팀 전체가 같은 이해를 가져야 한다**는 것을 배웠다. 같은 이해가 없으면 같은 패턴도 제각각 쓰이고, 좋은 구조도 "위치 상의 비용"으로 돌아온다.
- 다시 한다면: **풀려는 문제(그리고 그 우선순위)를 먼저 정의**하고, 패턴은 그 문제에 맞을 때만, **팀의 공통 이해를 먼저 맞춘 뒤** 도입하겠다.

## 면접 답변 스크립트 (2~3분)

> "제가 입사 초기에 오래 맡은 게 계정·구독 클라이언트인데요. 회사가 크레딧 기반에서 구독제로 비즈니스 모델을 바꾸면서, 플랜 업그레이드나 시트 구매 같은 결제·권한 기능을 FE에서 전담해 설계·구현했습니다.
>
> 이때가 제가 프론트엔드 아키텍처를 본격적으로 공부한 시기예요. 코드가 기준 없이 커지면서 어디를 고치면 어디가 깨질지 모르는 상태가 불편해서, FSD로 폴더 구조를 잡고, Compound Component·Render Props로 컴포넌트 관심사를 나누고, ErrorBoundary로 에러 처리를 선언적으로 바꾸고, 비즈니스 에러는 커스텀 에러 클래스로 분기하는 식으로 정리했습니다. 테스트 코드의 필요성도 이때 처음 느껴서 msw 기반으로 단위·통합 테스트를 도입했고요.
>
> 그런데 돌아보면 한계가 분명했어요. FSD를 도입했는데도 '이 파일을 어디에 넣어야 하지'를 매번 상의하느라 시간이 많이 들었고, 디자인 패턴은 굳이 안 써도 되는 곳에 일관성을 명분으로 넣은 경우가 많았습니다. 게다가 제가 제안한 방향을 팀원들이 다르게 이해해서, 같은 패턴인데 쓰는 방법이 제각각이 되더라고요.
>
> 그러면서 깨달은 게 — 디자인 패턴은 원래 오랜 기간 누적된 공통 문제를 푸는 해법인데, 저는 그 패턴이 *어떤 문제를 푸는지*를 정확히 이해하지 못한 채 도입했던 거예요. 그래서 지금은, 기술을 도입할 때 항상 '지금 우선순위가 가장 높은 문제가 뭔지'를 먼저 정의하고, 패턴은 그 문제에 맞을 때만, 그리고 팀이 같은 이해를 가진 상태에서 도입해야 한다고 생각합니다. 구조 자체가 나쁜 건 아니었어요 — 실제로 그 코드들은 이후 모노레포로 옮겨가면서도 그대로 살아남았고, 제 코드라는 생각엔 지금도 변함이 없습니다. 배운 건 '좋은 구조'가 아니라 '도입의 전제'였죠."
